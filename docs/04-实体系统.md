# 04 · 实体系统：NPC 的 AI 分派

本篇讲 Terraria 的 NPC 是怎么"思考"的：一个 `NPC` 对象每帧如何从"我是谁"推导到"我要做什么"，
`aiStyle` 这个整数如何被展开成 120 多个行为分支，状态又是怎样通过 `ai[]` 数组在帧之间传递。
表现层（Gore/Dust）只讲它与 AI 的耦合关系，不展开粒子系统本身。

---

## 一句话结论

Terraria 的 NPC AI 是**以 `aiStyle` 整数为键的手写巨型分支**：`NPC.AI()`（`Terraria/NPC.cs:19858`）
用一条 2000 多行的 `if / else if` 链把 0~127 号风格分派到同文件里约 120 个 `AI_xxx_名字()` 私有方法，
每个方法只读 `ai[0..3]` / `localAI[0..3]` 这 8 个 float 作为全部持久状态，并直接读写
`Main.player[target]`、`Main.tile`、`Main.dust`、`Main.gore` 等全局单例；
真正的"引擎"只是 `NPC.UpdateNPC()`（`Terraria/NPC.cs:91257`）里那一句 `AI()` 调用（`Terraria/NPC.cs:91407`）。

---

## 关键数据结构

### NPC 对象里与 AI 直接相关的位置

| 成员 | 定义位置 | 工程含义 |
| :--- | :--- | :--- |
| `aiStyle` | `Terraria/NPC.cs:6458` | AI 分派键，0~127；决定走哪个分支 |
| `ai[4]` | `Terraria/NPC.cs:6452`（数组长度 `maxAI`，见 `Terraria/NPC.cs:6052`） | **同步状态**：参与网络同步，客户端/服务端必须一致 |
| `localAI[4]` | `Terraria/NPC.cs:6454` | **本地状态**：纯客户端表现或服务端内部计数，不进网络包 |
| `target` | `Terraria/NPC.cs:6464` | 当前目标索引；玩家用 0~254 |
| `targetRect` / `oldTarget` | 见 `Terraria/NPC.cs:78356` 附近的赋值 | 目标包围盒缓存，以及上一帧目标（用于判断是否需要发网络更新） |
| `direction` / `directionY` | `directionY` 定义在 `Terraria/NPC.cs:6448` | 朝向；`directionY` 主要被飞行/跳扑类 AI 用来做上下瞄准 |
| `timeLeft` | `Terraria/NPC.cs:6462` | 活性倒计时，`CheckActive()` 每帧递减，归零即消失 |
| `townNPC` | `Terraria/NPC.cs:6544` | 城镇 NPC 标记，`SetDefaults` 里先统一清 `false`（`Terraria/NPC.cs:8541`），再按类型置 `true`（如向导 `Terraria/NPC.cs:9010`） |
| `netUpdate` / `netSpam` | `Terraria/NPC.cs:6140` / `Terraria/NPC.cs:6152` | 本帧是否需要广播；AI 里大量直接置 `netUpdate = true` 来"手动上报"状态切换 |

`target` 的编码在 1.4.4+ 扩展成了"玩家或 NPC"：`HasPlayerTarget` 判定 `0 <= target < 255`（`Terraria/NPC.cs:6697`），
`HasNPCTarget` 判定 `300 <= target < 300 + maxNPCs`（`Terraria/NPC.cs:6709`），`TranslatedTargetIndex` 负责去掉 300 偏移（`Terraria/NPC.cs:6723`）。
但是不是每个 NPC 都能选 NPC 当目标，由 `SupportsNPCTargets => NPCID.Sets.UsesNewTargeting[type]`（`Terraria/NPC.cs:6721`）控制，
这张表在白名单里显式列出了约 32 个 ID（`Terraria.ID/NPCID.cs:4777`）。

### `ai[]` 的语义是"每个 aiStyle 各自约定"

引擎**不规定** `ai[0]` 是什么，同一个槽位在不同 aiStyle 里含义完全不同，读 AI 代码时必须先锁定分支：

- aiStyle 4（克苏鲁之脑的仆从等，见 `Terraria/NPC.cs:19999` 起）：`ai[0]` 是**阶段编号**、`ai[1]` 是**子状态**、`ai[2]` 是**阶段计时器**，
  代码用 `ai[0] == 3f && ai[1] == 4f && ai[2] > num4` 这种形式驱动旋转速度（`Terraria/NPC.cs:20048`）。
- aiStyle 7（城镇 NPC）：`ai[0]` 是**特殊模式开关**，`ai[0] == 25f` 表示"正在微光转化/落地中"，
  此时强制 `dontTakeDamage = true`、清空速度与湿度（`Terraria/NPC.cs:53722`），并关闭重力（`Terraria/NPC.cs:91912`）。
- aiStyle 3（战士类）：`ai[0]` 被用作**通用倒计时**，例如符文巫师骑乘者被击落时把 `ai[0]` 先封顶到 1000f（`Terraria/NPC.cs:56766`），
  随后每帧 +1（`Terraria/NPC.cs:56768`），达到 1300 回落到 1000（`Terraria/NPC.cs:56770`）；离开击落态时若 `ai[0] >= 1000`
  则归零（`Terraria/NPC.cs:56775`~`Terraria/NPC.cs:56777`）。
- aiStyle 85：`ai[0]` 是行为状态机（0 选目标、1 追击、2 远距离、3 横向对准），`ai[1]/ai[2]` 是瞄准点坐标（`Terraria/NPC.cs:37282` 起）。

### 外部入口：谁给了初始 ai

`NPC.NewNPC` 直接把 4 个 float 塞进新实体（`Terraria/NPC.cs:81451` 签名，`Terraria/NPC.cs:81478` 赋值）。
这就是为什么 Boss 召唤物出生时"已经在某个阶段"：父实体的 AI 用 `ai[3]` 之类记录的子状态直接当参数传下去，
例如月之领主的真眼生成把父级的 `ai[3]` 透传给子眼（`Terraria/NPC.cs:41568`）。

## 执行流程

### 第 1 步：全局驱动循环

`Main.UpdateWorld_NPCs()` 先做整批准备（清空各玩家的 `nearbyActiveNPCs`、重建活跃 NPC 索引、推进
`NPC.offSetDelayTime` 错峰计数器），再对 `maxNPCs` 个槽位逐个调用 `npc[k].UpdateNPC(k)`
（`Terraria/Main.cs:18072` 起，调用点 `Terraria/Main.cs:18126`）。每个 NPC 的更新被 `try/catch` 包住，
出错时把槽位重置成新对象而不是让整个世界崩溃（`Terraria/Main.cs:18139`）。

> 折叠提示：上面这只是普通 `for` 循环，没有 lambda；但 `UpdateWorld_NPCs` 在 `Main.Update` 里是被
> `using (SwapRandom("UpdateNPCs"))` 包着调用的（`Terraria/Main.cs:17942`），编译器会把它展开成
> try/finally + `IDisposable`。读的时候脑内折叠成"这一段用独立的随机数流"即可。

### 第 2 步：UpdateNPC 的前置工作

`UpdateNPC(i)`（`Terraria/NPC.cs:91257`）的骨架是固定顺序：

1. `whoAmI = i`，把自己在 `Main.npc` 中的下标固化，后续 AI 里 `whoAmI` 用于让别的 NPC 反查自己；
2. 网络平滑：非服务端且未禁用平滑时，逐步消解 `netOffset`（客户端对服务端位置的视觉修正量），
   城镇 NPC 走回家位置附近时直接清零（条件 `Terraria/NPC.cs:91264`，清零位置 `Terraria/NPC.cs:91292`）；
3. 外部表现：`UpdateAltTexture`（`Terraria/NPC.cs:91298`）、施法光源（`Terraria/NPC.cs:91304`）、传送视觉（`Terraria/NPC.cs:91306`）；
4. 特殊类型的前置：aiStyle 7 掉到世界底部以下直接秒杀（`Terraria/NPC.cs:91313`）；
5. Buff 管线：重置标志 → 设置标志 → 灵魂汲取 → 过期清理 → DOT 伤害 → Buff 特效 → 血月变身（`Terraria/NPC.cs:91357`~`Terraria/NPC.cs:91363`）；
6. `UpdateNPC_UpdateGravity(out maxFallSpeed)` 让各类型调整重力与终端速度（`Terraria/NPC.cs:91364`）；
7. 死亡早退：`life <= 0` 直接置 `active = false` 并返回，**不进入 AI**（`Terraria/NPC.cs:91369`）；
8. 记录 `oldTarget / oldDirection / oldDirectionY`（`Terraria/NPC.cs:91377`），处理 `gfxOffY`（踩台阶的视觉抬升，`Terraria/NPC.cs:91381`）与传送门；
9. **调用 `AI()`**（`Terraria/NPC.cs:91407`）。

### 第 3 步：AI() 内——分派

`NPC.AI()`（`Terraria/NPC.cs:19858`）的写法有两种形态：

- `aiStyle 0`（"无 AI"）就地实现：绑定类 NPC 自动标 `homeless`，扫描 `Main.player[i].talkNPC == whoAmI`
  决定是否变形（仙子/巫医等，`Terraria/NPC.cs:19860`）；随后调 `TargetClosest()` 只为了转身，最后一句
  结尾是水平阻尼 `velocity.X *= 0.93f`（`Terraria/NPC.cs:19976`）后 `return`（`Terraria/NPC.cs:19982`）。
- `aiStyle 1~19` 用一串独立的 `if (aiStyle == N) { ...; return; }`（`Terraria/NPC.cs:19984` 起）；
  `aiStyle 20` 起改成 `else if` 链（第一个 `else if` 在 `Terraria/NPC.cs:24729`），
  一直到 `aiStyle 127`（`Terraria/NPC.cs:41539`）。`AI()` 本身没有返回值、没有 `default` 分支，
  遇到未列出的值就什么都不做。

> 关于"switch"：源码里 1~19 的 `if`、20 以后的 `else if` 是**手写的顺序比较**，不是 C# `switch` 语句。
> 真正用 `switch (aiStyle)` 的地方在别处（例如渲染分支里的 `switch (type)`）。这在工程上等价于
> "跳转表退化成了线性比较"，但因为每个合法值最多比较到第 128 次、且分支体巨大，开销可以忽略。

两种形态混用（早期分支单独成 `if`，后期成 `else if`）是历史堆积的结果：新 aiStyle 都是在文件末尾追加，
作者逐渐把"每个分支自带 return"的写法换成了链式 `else if` + 末尾统一收口。

分派目标绝大多数是 `AI_xxx_名字()` 形式的方法，例如：

| aiStyle | 方法 | 行号 |
| :--- | :--- | :--- |
| 1 | `AI_001_Slimes` | `Terraria/NPC.cs:60920` |
| 3 | `AI_003_Fighters` | `Terraria/NPC.cs:56410` |
| 6 | `AI_006_Worms` | `Terraria/NPC.cs:51490` |
| 7 | `AI_007_TownEntities` | `Terraria/NPC.cs:53499` |
| 84 / 85 | `AI_084_LunaticCultist` / 内联 | `Terraria/NPC.cs:65035` / `Terraria/NPC.cs:37284` |
| 107~127 | 各 Boss / 小动物 | 见 `Terraria/NPC.cs:41459`~ `Terraria/NPC.cs:41539` |

注意 aiStyle 85 并没有独立方法，整段逻辑内联在 `AI()` 里（`Terraria/NPC.cs:37284`），
这印证了"内联 vs 抽方法"只是随手选择，没有统一规范。

### 第 4 步：分支内部——目标选择

绝大多数敌对分支的第一句是 `TargetClosest()`（`Terraria/NPC.cs:78330`）。它的逻辑是：

1. 遍历 `0..254` 号玩家，筛掉死亡/未激活/幽灵（`Terraria/NPC.cs:78336`~`Terraria/NPC.cs:78338`）；
2. 对每个候选调 `TryTrackingTarget`（`Terraria/NPC.cs:78362`）：
   - **距离用曼哈顿距离** `|dx| + |dy|` 而非欧氏距离（`Terraria/NPC.cs:78365`），省一个开方；
   - 再减去玩家的 `aggro`（仇恨值）得到"评分"，`aggro` 越高越容易被选中；
   - 玩家佩戴了针对该怪物的 `npcTypeNoAggro` 且怪物已有朝向时，评分 +1000，等于"退避"；
   - 玩家携带的 tank 召唤物若在 200 像素内且视线可达（曼哈顿距离减 200 后小于当前评分且小于 200，并 `Collision.CanHit`），
     会压过玩家成为 `tankTarget` 优先目标（`Terraria/NPC.cs:78383`~`Terraria/NPC.cs:78388`）——且 `tankTarget` 存的是
     **投射物下标**，`SetTargetTrackingValues` 用 `Main.projectile[tankTarget]` 建 `targetRect`（`Terraria/NPC.cs:78396`）；
3. `SetTargetTrackingValues`（`Terraria/NPC.cs:78392`）刷新 `targetRect`（`Terraria/NPC.cs:78414`）、根据目标中心相对自己的位置设定
   `direction/directionY`（`Terraria/NPC.cs:78399`），并处理 `confused` 反向（`Terraria/NPC.cs:78455`）；
4. 若 `direction/directionY/target` 任一发生变化且没有卡碰撞，置 `netUpdate = true`（`Terraria/NPC.cs:78457`），
   最后写 `targetSetFrame = Main.EverLastingTicker` 作为"本帧已选过目标"的时间戳。

world-吞噬者（Wall of Flesh）用的是变体 `TargetClosest_WOF`，额外要求 `Main.player[i].gross`（`Terraria/NPC.cs:78346`）。

AI 分支对目标的使用方式是裸的：直接 `Main.player[target].Center`，**没有"目标是否存在"的防御**。
如果分支提前 `return` 没选目标，`target` 可能是 `SetDefaults` 时 `ClearTarget()` 设的 255（`Terraria/NPC.cs:43357`），
此时访问 `Main.player[255]` 会越界——所以每个分支都要自己保证先调用过 `TargetClosest()`。

### 第 5 步：分支内部——状态机与移动

以 aiStyle 3（`AI_003_Fighters`，`Terraria/NPC.cs:56410`）为例，可以看清这类"万金油"分支的组织方式：

- 先用 `type == xxx` 处理个别怪物的一次性行为（石像鬼石化、幽灵状态切换等，`Terraria/NPC.cs:56417` 起）；
- 再用 `ai[...]` 做阶段判定（如 `ai[0]` 倒计时、`ai[3]` 存"正被谁击落"，`Terraria/NPC.cs:56764`~`Terraria/NPC.cs:56777`）；
- 最后是通用**跳扑逻辑**：`velocity.X += num305 * direction`（`Terraria/NPC.cs:24726`）配合
  `velocity.Y += num305 * directionY`（`Terraria/NPC.cs:24727`）形成朝目标方向的匀加速；
  这段属于 aiStyle 20（`Terraria/NPC.cs:24729`），但 aiStyle 3 等分支的结构一致；
- 各种 `switch (type)` / `if (type == ...)` 穿插其中，让 165 个共享 aiStyle 3 的 NPC 各自微调参数
  （统计方式：`grep 'aiStyle = 3;' Terraria/NPC.cs` 共 165 处）。

也就是说，aiStyle 解决的是"**一类移动/攻击套路的骨架**"，`type` 解决的是"**这只怪的具体数值与例外**"。
两者的关系不是干净的继承，而是骨架里塞满了 `type` 特判——读代码时如果只盯着 ai[0]，会漏掉大量行为。

### 第 6 步：物理与收尾

`AI()` 返回后，`UpdateNPC` 继续：

1. 依次递减 `immune[256]` 受击无敌计时（`Terraria/NPC.cs:91436`~`Terraria/NPC.cs:91440`）；
2. 非 `noGravity` 的实体每帧加一次 `gravity` 并按 `maxFallSpeed` 钳制（`Terraria/NPC.cs:91454`~`Terraria/NPC.cs:91456`）；
   此前若实体既非 `noGravity` 也非 `noTileCollide`，会先检测所在 tile 是否已加载，未加载则直接把 `gravity` 与速度清零
   （`Terraria/NPC.cs:91443`~`Terraria/NPC.cs:91452`）——**所以 AI 里写的 `velocity.Y -= 0.04f` 之类其实是在与重力拔河**
   （`noGravity` 的飞行系除外），AI 改的是速度而重力每帧都会补回来；
3. 友方/城镇 NPC 的溺水、回血、被敌对生物攻击检测（`Terraria/NPC.cs:91466`，城镇 NPC 额外 `CheckDrowning` 见 `Terraria/NPC.cs:91468`）；
4. 碰撞与位移：`noTileCollide` 为假走 `UpdateCollision()`（`Terraria/NPC.cs:91483`），否则直接
   `position += velocity` 并做水体检测（`Terraria/NPC.cs:91487`）；
5. 特定类型踩到机关方块时重置自己的 `ai[0..2]`（`Terraria/NPC.cs:91493`）；
6. `CheckDialogue()` → `FindFrame()` → 拖尾 → 网络上报 → `CheckActive()` → 清 `netUpdate/justHit`
   （`Terraria/NPC.cs:91499`~`Terraria/NPC.cs:91505`）。

其中 `FindFrame()`（`Terraria/NPC.cs:67325`）本来只是"按速度选行走帧"：开头 `position += netOffset`（`Terraria/NPC.cs:67327`），
随后先按 `aiAction`（`Terraria/NPC.cs:67338` 的 `if (aiAction == 0)`）挑基础帧，再进入一个巨大的 `switch (type)`
让 Boss 的攻击帧独立计算（`Terraria/NPC.cs:67346` 起），再次说明**类型特判散落在各子系统**。

`CheckActive()`（`Terraria/NPC.cs:78575`）负责消失：城镇 NPC 直接跳过（`Terraria/NPC.cs:78577`），
否则比较玩家是否在 `activeRange` 矩形内（`Terraria/NPC.cs:78583`）、是否在更大的 `sWidth/sHeight` 缓冲区内
（`Terraria/NPC.cs:78584`，命中会把 `timeLeft` 重置为 `activeTime` 并 `continue` 跳过该玩家）；
之后 `timeLeft--`（`Terraria/NPC.cs:78667`）到 0 就 `active = false`（`Terraria/NPC.cs:78673` 起），
服务端还要发 23 号包通知客户端，并把高价值怪物交给 `RevengeManager.CacheEnemy`。
`EncourageDespawn(t)`（`Terraria/NPC.cs:7276`）就是 AI 里主动"求消失"的接口，白天/目标死亡时的飞行系怪物常见。

### 第 7 步：城镇 NPC 与敌怪的差异

同一套 `UpdateNPC` 框架下，城镇 NPC 的差异集中在三点：

1. **不被选中**：`friendly` 在 `SetDefaults` 里默认 `false`，城镇 NPC 分支再置 `true`（向导见 `Terraria/NPC.cs:9011`）；
   `TargetClosest` 只在敌对分支里调用，aiStyle 7 自己只在"被攻击后报复"时调 `TargetClosest()`（`Terraria/NPC.cs:53783`）。
2. **不会超时消失**：`CheckActive` 对 `townNPC` 直接 `return`（`Terraria/NPC.cs:78577`）。
3. **有家**：`AI_007_TownEntities`（`Terraria/NPC.cs:53499`）开头就同步 `defDefense`、按 `combatBookWasUsed`
   等全局解锁状态重算 `lifeMax/defense`（`Terraria/NPC.cs:53548`）；家坐标 `homeTileX/homeTileY`
   由 `SetDefaults` 初始化为 -1（`Terraria/NPC.cs:8544`~`Terraria/NPC.cs:8545`），`homeless` 时四处游荡。
   找家/回家/坐下由 `AI_007_FindGoodRestingSpot`、`AI_007_TownEntities_TeleportToHome`（`Terraria/NPC.cs:56195`）等辅助方法负责；
   家被摧毁时的 `homelessDespawn` 路径本篇未逐行验证。
   它的辅助方法成套出现：找休息点 `AI_007_FindGoodRestingSpot`（`Terraria/NPC.cs:53328`）、
   强制坐下 `AI_007_TryForcingSitting`（`Terraria/NPC.cs:53397`）、存盘状态 `AI_007_TownEntities_UpdateSavedStates`
   （`Terraria/NPC.cs:53468`）、走路预测 `AI_007_TownEntities_GetWalkPrediction`（`Terraria/NPC.cs:56225`）。
4. **可被"绑定/变形"**：aiStyle 0 的绑定 NPC 在玩家与之对话时通过 `AI_000_TransformBoundNPC`
   （`Terraria/NPC.cs:45354`）换成正式的城镇 NPC，并调用 `AI_007_TownEntities_UpdateSavedStates` 补上家状态。

`townNPC` 与 `isLikeATownNPC`（`Terraria/NPC.cs:6880`，对 453 号额外返回真）不是同一个概念：
前者是 `SetDefaults` 里逐类型写死的标记，后者是"行为像城镇 NPC"的口径，`CanTalk`/`CanBeTalkedTo`
（`Terraria/NPC.cs:6657` / `Terraria/NPC.cs:6669`）都用后者判断。

### 第 8 步：表现层——Gore 与 Dust

AI 里看到 `Dust.NewDust(...)` 和 `Gore.NewGore(...)` 混用时，要分清两者是**不同预算、不同生命周期的系统**：

- **Dust**（`Terraria/Dust.cs`）：固定 6000 槽位，`NewDust`（`Terraria/Dust.cs:75`）在服务端、暂停、世界生成期间
  直接返回哨兵值 6000（`Terraria/Dust.cs:77` 起），并且做**屏幕裁剪**：以屏幕外扩 400 像素为界，
  不在范围内也返回 6000（`Terraria/Dust.cs:101` 附近）。槽位占用率超过 `maxDustToDraw` 的 50%~90%
  时会按概率拒绝新建粒子（`Terraria/Dust.cs:114` 起），这就是高负载时粒子的"自动降级"。
  返回的 6000 是一个**无效下标**，所以源码里 `Main.dust[NewDust(...)].velocity *= ...` 这种写法在服务端会抛异常——
  AI 里的 Dust 调用通常伴随 `Main.netMode != 1` 之类的保护或放在纯客户端路径里。
- **Gore**（`Terraria/Gore.cs`）：固定 600 槽位，`NewGore`（`Terraria/Gore.cs:1306`）在服务端/暂停时返回 600（无效下标），
  只做**首个空槽**分配、不做屏幕裁剪（`Terraria/Gore.cs:1332` 起）；会对速度加一次随机上抛与水平抖动（`Terraria/Gore.cs:1339`），
  并按 `GoreID.Sets.IsDrip` 等表调整 `sticky/timeLeft/behindTiles`（`Terraria/Gore.cs:1364`）。
- 更新入口：Gore 由 `Main.UpdateWorld_Gores()`（`Terraria/Main.cs:18145`）调 `gore[i].Update()`
  （`Terraria/Gore.cs:313`，内部同样按 `GoreID.Sets.SpecialAI[type]` 做特殊分支）；Dust 由
  `Main.UpdateWorld_Dust()`（`Terraria/Main.cs:18220`）调 `Dust.UpdateDust()`（`Terraria/Dust.cs:423`，
  逐槽更新并累加 `dCount` 用于上文的降级判定）。
- 两者在服务端都直接 `return`（`Terraria/Gore.cs:315`、`Terraria/Dust.cs:425`）——表现层完全是客户端的。

因此 AI 代码里的 `if (Main.rand.Next(5) == 0) Dust.NewDust(...)` 这类写法（例如 aiStyle 4 的 `Terraria/NPC.cs:20420` 附近）
**不会因为服务端没有粒子而影响逻辑**，AI 只是顺手借用了 `Main.rand` 这个全局随机源；但要注意这意味着
客户端的 AI 随机序列与服务端不同（服务端调用 NewDust 会立即返回，消耗的随机数次数不同），
状态同步必须依赖 `ai[]` 而不是"两边算出来会一样"。

## 设计要点与取舍

**1. 用 4 个 float 表达全部状态，是网络协议倒逼的设计。**
`ai[]` 长度固定为 4（`Terraria/NPC.cs:6052`），网络包里每个 NPC 就只要带 4 个 float + 位置 + 速度。
代价是所有复杂 Boss 都要"压榨"这 4 个槽位：让不同分支复用同一槽位、用"1000 以上的值代表击落态、其增量代表计时"这类
约定的复合编码（`ai[0]` 封顶 1000 后逐帧 +1，`Terraria/NPC.cs:56766`~`Terraria/NPC.cs:56770`），可读性极差但同步成本最低。1.4 之后加入的 `localAI` 起到"缓存/纯客户端"的正交作用，
比如蠕虫的 `localAI[1]` 只用于"已经播过死亡音效"（`Terraria/NPC.cs:51492`），不需要同步。

**2. `aiStyle` 是"行为模板"，`type` 是"参数与例外"。**
一个 aiStyle 服务几十甚至上百个 type，让新怪物的开发成本极低（填 `SetDefaults` 的数值 + 复用一个风格）。
代价是模板内堆积了大量 `if (type == N)` 特判，导致分支方法动辄上千行，任何修改都可能波及其它生物。
这也是为什么 `AI_003_Fighters`（`Terraria/NPC.cs:56410` 起，到下一个方法前约 4500 行）、`AI_007_TownEntities`（`Terraria/NPC.cs:53499` 起，约 1600 行）会膨胀到这种体量。

**3. 巨型链式分派的性能取舍。**
120 多个分支的顺序比较在极端 aiStyle（127）时最多 128 次整数比较，相比分支内部的几千行逻辑可忽略；
换来的是"新风格直接 append 到末尾"的极低合并冲突成本（这也是社区源码 modding 几乎没有侵入式改 `AI()` 的原因）。
但读者需要自己维护"aiStyle → 方法名 → 行号"的索引，源码里没有集中表。

**4. 目标系统的 1.4.4+ 扩展是缝合式的。**
`target` 从"玩家索引"扩展成"玩家或 NPC"靠 300 的偏移量实现（`Terraria/NPC.cs:6709`），
旧的 `TargetClosest` 仍然只扫玩家（`Terraria/NPC.cs:78333`），新能力由各分支按需调用新函数；
`SupportsNPCTargets` + ` 白名单只覆盖 32 个类型（`Terraria.ID/NPCID.cs:4777`），说明绝大多数怪物仍然只会打玩家。

**5. 表现层与逻辑层解耦，但共享随机源。**
Dust/Gore 在服务端是空操作，逻辑层不需要关心；但它们共用 `Main.rand`，AI 里为表现而掷的骰子会消耗服务端的随机序列——
所以**不能用 "两边随机数一致" 来推断状态同步**，一切状态必须走 `ai[]`。

**6. 城市 NPC 是"特殊化的敌怪"。**
它复用了同一套 `UpdateNPC`（共享碰撞、Buff、施法、帧动画），只在 `CheckActive`、`AI()` 的分支
和几处 `townNPC` 短路里做区别。好处是城镇 NPC 自动获得所有战斗系统（会被打、会回血、会溺水），
代价是每个系统里都多了一条 `if (townNPC)`。

**7. 服务端/客户端不是对称模拟。**
从 `main.cs` 的更新顺序看，只是"同样的 `UpdateNPC` 在两边各跑一遍"，但 `NewDust` 的哨兵返回、
`netOffset` 的视觉平滑、`localAI` 的本地缓存都意味着**客户端的结果永远只是"近似"**。
读 AI 代码时，凡是可能改变 `ai[]` 的分支，都会看到 `Main.netMode != 1` 保护（例如 `Terraria/NPC.cs:91374` 附近的死亡处理、
`Terraria/NPC.cs:92574` 的微光转化），这是"权威在服务端"的直接体现。
