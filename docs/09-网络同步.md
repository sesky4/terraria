# 网络同步

> 适用范围：Terraria v1.4.5.8 反编译源码。路径均相对 `decompiled/Terraria/`。
> 阅读提示：反编译出的 `num/num2/flag/flag2/val` 等机械命名，本文统一转写为工程含义（目标速度、是否已初始化等）；`foreach` / `using` / `lock` 展开的 try-finally、以及 `ReadCallback` 之类的匿名委托可脑内折叠回原始语法。

## 一句话结论

Terraria 的联机是**权威服务器（authoritative server）+ 客户端本地预测**的模型：`Main.netMode` 用 0/1/2 区分单机/客户端/服务端；所有数据都是"一条条独立报文"，每条报文自带 2 字节长度，`MessageID` 是 1 字节的消息类型；客户端只负责把**输入（按键位）**发给服务端，其余一切（位置结算、伤害、NPC 生成、地块改动）都由服务端计算并广播。收发走两套平行机制：**旧路径**是逐客户端的 `MessageBuffer`（`NetMessage.SendData` / `MessageBuffer.GetData`），**新路径**是 `NetManager` + `NetModule` 插件式模块（消息 82 承载），供液体、文字、Ping、Bestiary 等高频/子系统自定义协议。底层传输被 `ISocket` 抽象成 `TcpSocket`（专服/直连）与 `SocialSocket`（Steam P2P / WeGame P2P）两种实现。

## 关键数据结构

### 连接状态容器（Terraria/Netplay.cs）
- `Netplay.Clients`：`RemoteClient[256]`（`Netplay.cs:39`），服务端视角下每个玩家槽位一个；下标即玩家 `whoAmI`。
- `Netplay.Connection`：`RemoteServer`（`Netplay.cs:41`），客户端视角下唯一的"服务端连接"。
- `Netplay.TcpListener` / `ListenPort=7777`（`Netplay.cs:51-53`）：TCP 监听句柄与端口。
- `Netplay.fullBuffer`（`Netplay.cs:71`）：专用于"服务器已满"等早期踢人报文的独立写缓冲，避免与正常发送争用。`KickClient(ISocket, msg)`（`Netplay.cs:193-215`）复用它组装 Kick(2) 并经裸 socket 的 `AsyncSend` 发出；目前只有 `OnConnectionAccepted` 的无空槽分支调用它（`Netplay.cs:187-190`），即实际只承载 `CLI.ServerIsFull`。

### MessageBuffer：每连接一读一写（Terraria/MessageBuffer.cs）
`MessageBuffer` 同时承载**收包**与**发包**两套缓冲区，长度为常量 `readBufferMax = writeBufferMax = 131070`（`MessageBuffer.cs:33-35`），即单连接读缓冲累积上限约 128 KiB。
- 读侧：`readBuffer` / `reader` / `totalData`（已累积但未解析的字节数）/ `whoAmI`（此缓冲属于哪个客户端；客户端连接固定用 256）。
- 写侧：`writeBuffer` / `writer` / `broadcast` / `writeLocked`。
- `broadcast`（`MessageBuffer.cs:37`）是服务端"此槽位是否已完成握手、可以收广播"的开关，未完成的连接不发普通状态更新。
- `NetMessage.buffer = new MessageBuffer[257]`（`NetMessage.cs:54`）：下标 0..255 对应服务端各客户端，下标 256 是客户端↔服务端的专用槽位；`Netplay.Initialize()` 里统一实例化并写 `whoAmI`（`Netplay.cs:729-744`）。

### RemoteClient / RemoteServer：状态机与超时
`RemoteClient`（`RemoteClient.cs`）关键字段：
- `State`（`RemoteClient.cs:27`）：握手状态，见下文状态码表；`State==10` 即"已进入世界"。
- `TimeOutTimer`（`RemoteClient.cs:29`）：超时计数；任何一条合法报文都会把它清零（`MessageBuffer.cs:127-135`）。
- `TileSections[,]` / `TileSectionsCheckTime[,]`（`RemoteClient.cs:31-33`）：该客户端**拥有（已下发）**的区块、以及区块最近一次激活的时间戳。
- `SpamProjectile / SpamAddBlock / SpamDeleteBlock / SpamWater` 与对应 `*Max`（`RemoteClient.cs:39-53`）：反作弊的"行为积分"，超阈值直接踢人。
- `ReadBufferFull`（`RemoteClient.cs:57`）：只读属性，`NetMessage.buffer[Id].RemainingReadBufferLength < ReadBuffer.Length`；真正消费它的是 `TryRead`——为真时不再发起新的 `AsyncReceive`（`RemoteClient.cs:266-284`），由此形成背压。

`IsSectionActive`（`RemoteClient.cs:221-225`）：区块里记录的时间戳 + `ActiveSections.SectionInactiveTime`（`Terraria.DataStructures/ActiveSections.cs:9`，常量 60）≥ 当前 `Main.GameUpdateCount`，即"该区块在最近 `SectionInactiveTime` 个更新周期内被激活过"（并非"当前仍在视野内"；60 依赖 60Hz 更新率，约 1 秒）。

### 消息编号（Terraria.ID/MessageID.cs）
`MessageID` 是 163 个 `const byte` 的序号表（`MessageID.cs:5` 起，`Count = 163` 在文件末尾）。带 `[Old("Deprecated.")]` 的常量仍占号但已废弃（如 `Unknown15`、`Unused25/26`、`LiquidUpdate=48`）。常用几项：

| 编号 | 常量 | 用途 |
|---|---|---|
| 1 / 2 / 3 | Hello / Kick / PlayerInfo | 版本握手 / 踢人 / 分配槽位 |
| 4 / 5 | SyncPlayer / SyncEquipment | 外观信息 / 单个物品槽 |
| 6 / 7 / 8 / 9 | RequestWorldData / WorldData / SpawnTileData / StatusTextSize | 世界元数据与初始区块 |
| 10 / 13 / 14 | TileSection / PlayerControls / PlayerActive | 地块块 / 输入帧 / 上下线 |
| 17 / 20 | TileManipulation / AreaTileChange | 单格改动 / 小方块区域改动 |
| 21 / 22 / 23 / 27 | SyncItem / ItemOwner / SyncNPC / SyncProjectile | 世界物品 / 归属 / NPC / 投射物 |
| 28 / 162 | DamageNPC / DamageNPCAck | 伤害请求 / 伤害确认 |
| 82 | NetModules | 模块化协议总入口 |
| 154 | Ping | 心跳测延迟 |

注意 `GetData` 会拒绝 `>= MessageID.Count` 的类型（`MessageBuffer.cs:137-140`），因此增删协议号必须两端同步改。

### 数据包物理格式
每条报文 = `[uint16 总长(小端, 含自身)] [uint8 消息类型] [负载]`。发送侧写了 2 字节占位并在结尾回填总长（`NetMessage.cs:1691-1698`）；接收侧按 2 字节长度切分（`NetMessage.cs:2555`）。模块包（消息 82）在负载前额外有 3 字节：`[uint8 魔数 82] [uint16 模块号]`，所以 `NetPacket.HEADER_SIZE = 5`（`Terraria.Net/NetPacket.cs:9`，5 = 2 长度 + 1 消息 82 + 2 模块号），构造时依次写入（`NetPacket.cs:28-30`）。

## 执行流程

### 1. 连接建立与握手状态机
**服务端入口**：`StartServer` → `InitializeServer`（`Netplay.cs:242`）把 `Main.netMode=2`、创建 256 个 `RemoteClient`，再 `StartListening`（`Netplay.cs:222`）同时挂 `SocialAPI.Network.StartListening`（Steam/WeGame 大厅）和 `TcpListener`。新连接到达 `OnConnectionAccepted`（`Netplay.cs:177`）时取空槽、绑定 Socket；无空槽则用 `fullBuffer` 单独发 `ServerIsFull` 踢人（`Netplay.cs:189-216`）。

**客户端接入**：`StartTcpClient` 起后台线程跑 `TcpClientLoop`（`Netplay.cs:386-398`），`ClientLoopSetup`（`Netplay.cs:425`）把 `Main.netMode=1`、重建 `RemoteServer`；Steam 则走 `OnConnectedToSocialServer` → `SocialClientLoop`（`Netplay.cs:371`）。

**服务端 `RemoteClient.State` 迁移**：
1. `State=0`：只接受 Hello(1)。`GetData` 对 `State==0` 收到非 1 的报文直接 `BootPlayer`（`MessageBuffer.cs:160-168`）。
2. 收到 Hello：校验版本串 `"Terraria"+326`（`MessageBuffer.cs:203`；发送侧同串在 `NetMessage.cs:132`）。无密码 → `State=1` 并回 PlayerInfo(3)；有密码 → `State=-1` 并回 RequestPassword(37)。`State==-1` 时除 SendPassword(38) 外的报文一律踢（`MessageBuffer.cs:158-162`）；密码校验通过后回到 `State=1`（`MessageBuffer.cs:2218-2228`）。
3. `State<10` 期间只放行白名单消息（12、16、42、50、38、68、93、147、161 等，`MessageBuffer.cs:165-172`），其余一脚踢出。
4. 客户端发 SyncPlayer(4)：服务端存下名字并做重名/长度/难度检查（`MessageBuffer.cs:353-395`）。
5. 客户端发 RequestWorldData(6)：服务端置 `State=2` 并发 WorldData(7) + 同步入侵状态（`MessageBuffer.cs:462-471`）。
6. 客户端发 SpawnTileData(8)：服务端置 `State=3`，给出"要发多少个区块"的状态文本，然后逐个 `SendSection`（`MessageBuffer.cs:807-846`）。
7. 客户端发 PlayerSpawn(12)：`State=3→10`，打开本槽的 `broadcast = true`，`SyncConnectedPlayer` 广播该玩家入场（`MessageBuffer.cs:925-938`）。

**客户端 `Netplay.Connection.State`**：0 未连 → 1 已连（发 Hello，`Netplay.cs:472`）→ 收到 PlayerInfo 变 2（`MessageBuffer.cs:232-236`）→ 收到 WorldData 走 4（经 3，`MessageBuffer.cs:654-658`）→ 清空世界后变 5（`Netplay.cs:481-502`）→ 世界清空完成后变 6 并发 SpawnTileData（`Netplay.cs:508-513`）→ 收到 InitialSpawn(49) 变 10（`MessageBuffer.cs:2449-2456`）。这条状态机同时驱动主菜单上的进度文案（`Netplay.cs:471-514`）。

### 2. 收包：从 Socket 到 GetData
- **服务端**：`ServerLoop`（`Netplay.cs:287`）循环 `UpdateConnectedClients` → `RemoteClient.Update` → `TryRead`（`RemoteClient.cs:266`）→ `Socket.AsyncReceive(ReadBuffer, ..., ServerReadCallBack)`。回调里把字节交给 `NetMessage.ReceiveBytes(bytes, length, Id)`（`RemoteClient.cs:286` 起）。
- **客户端**：`InnerClientLoop`（`Netplay.cs:459`）在 `IsDataAvailable() && !ReadBufferFull` 时发起 `AsyncReceive`（`Netplay.cs:522-525`），回调 `RemoteServer.ClientReadCallBack` 调 `NetMessage.ReceiveBytes(ReadBuffer, length)`（`RemoteServer.cs:56` 起），`streamLength==0` 视为对端关闭。
- **字节入缓冲**：`ReceiveBytes`（`NetMessage.cs:2495-2519`）加锁把数据 `BlockCopy` 到 `buffer[i].readBuffer` 末尾、累加 `totalData` 并置 `checkBytes`；若 `BlockCopy` 越界抛异常，则客户端断线回菜单（`menuMode = 15`、`statusText = Error.BadHeaderBufferOverflow`），服务端置 `PendingTermination`。
- **解析**：`CheckBytes`（`NetMessage.cs:2521-2597`）在主线程执行：统一入口是 `Netplay.UpdateInMainThread()`（`Netplay.cs:747-758`），专服主循环在 `Main.cs:5878` 调用它、进入 `UpdateServerInMainThread` 对 0..255 逐个 `CheckBytes(i)`（`Netplay.cs:96-102`）；客户端主循环在 `Main.cs:17064` 调用它、进入 `UpdateClientInMainThread` → `NetMessage.CheckBytes()`（`Netplay.cs:333-338`）。它按 `while (剩余 >= 2)` 读 2 字节长度，`剩余 >= 长度` 才切出一条，调 `buffer.GetData(start+2, len-2, out messageType)`；处理完后把读取位置**强制**拨到"该条起点 + 长度"（`NetMessage.cs:2574`），防止某条消息少读字节污染下一条。末尾把半条残留数据 memmove 到缓冲头（`NetMessage.cs:2584-2588`）。
- **分发**：`MessageBuffer.GetData`（`MessageBuffer.cs:125`）先做"活性"处理——清零 `TimeOutTimer`（`MessageBuffer.cs:127-135`）、拒绝越界类型、做前述状态机准入检查——然后把 `reader` 定位到 payload（`MessageBuffer.cs:177-179`）并进入 `switch (messageType)` 的大分支（`MessageBuffer.cs:179` 起，覆盖 1..162）。
- **错误处理**：任何分支抛异常都被 `catch` 交给 `LogMessageError`（定义于 `NetMessage.cs:2593` 起）而不是崩溃；解析循环本身失败则丢弃全部缓冲（`NetMessage.cs:2576-2581`）。

### 3. 发包：SendData 的统一管道
`NetMessage.SendData`（`NetMessage.cs:81`）是所有旧协议的唯一出口，签名是 `(msgType, remoteClient, ignoreClient, text, number, number2..number7)`——由于 C# 不支持变长参数，全部负载被压成 1 个 int + 4 个 float + 3 个 int 的"万能槽位"，各分支按需挑用并自行决定序列化宽度（`short`/`byte`/`float` 混用）。
1. 单机（`netMode==0`）直接返回（`NetMessage.cs:83-86`）。
2. 少量"发送前改写类型"的特殊处理，例如 SyncItem(21) 若物品已消失则改为 151（`NetMessage.cs:88-103`）。
3. 选缓冲：服务端且 `remoteClient>=0` 用该客户端自己的 `buffer[remoteClient]`，否则用 256 号缓冲（`NetMessage.cs:114-117`）。**同一时刻只按一个客户端序列化**，靠 `lock (buffer[num])` 串行化。
4. 写入：先占 2 字节、写 1 字节类型，再按 `msgType` 分支写负载（巨大的 `switch`，`NetMessage.cs:129` 起）。
5. 回填长度并校验不超过 65535（`NetMessage.cs:1691-1698`）。
6. 分发：客户端 → `SendPacketToServer`（`NetMessage.cs:1859`）；服务端且 `remoteClient==-1` → 按类型走不同受众策略（见下文"状态同步策略"）；`remoteClient>=0` 则只发给那一个在线客户端（`NetMessage.cs:1828-1846`）。若目标是 Kick(2)，还会置 `PendingTermination`，让发送完成后有序断开（`NetMessage.cs:1854-1857`）。
7. `TrySendData`（`NetMessage.cs:68`）只是包一层 try/catch 的 `SendData`，返回是否成功，绝大多数调用点都用它。

`SendPacket`（`NetMessage.cs:1864-1884`）用 `AsyncSend` 真正发出：非专服发给 `Netplay.Connection.Socket`，专服发给对应 `Clients[remoteClient].Socket`；发送完成回调 `ServerWriteCallBack` 会把 `buffer[Id].spamCount` 减 1（`RemoteClient.cs:251-254`），这是"在途报文"计数。

### 4. 模块化协议（NetManager / NetModule）
- 注册：`NetworkInitializer.Load`（`Terraria.Initializers/NetworkInitializer.cs:9-25`）按固定顺序注册 15 个模块，模块号就是注册序号（`NetManager.Register`，`Terraria.Net/NetManager.cs:29-36`），**两端顺序必须一致**否则编号错位。
- 分发：消息 82 到达后 `MessageBuffer.cs:3238-3241` 直接 `NetManager.Instance.Read(reader, whoAmI, length)`；`NetManager.Read`（`NetManager.cs:53-64`）读 2 字节模块号查表调 `Deserialize`。
- 发送：模块自己 `NetModule.CreatePacket<T>()` 造包（`NetModule.cs:9-13`），默认 `maxSize = 65530` 为负载上限，`NetPacket` 构造时 `Length = size + HEADER_SIZE`、超过 65535 抛错（`NetPacket.cs:21-29`）；再用 `NetManager.SendToServer/SendToServerOrBroadcast/Broadcast` 等发出；单机模式下 `SendToSelf` 会直接把包当本地读入（`NetManager.cs:99-104`），实现"单机也走同一套逻辑"。
- 典型：`NetPingModule`（`Terraria.GameContent.NetModules/NetPingModule.cs:9-29`）客户端发坐标（Ping 模块注册为 3 号，`Terraria.Initializers/NetworkInitializer.cs:13`），专服收到后 `NetManager.Instance.Broadcast(Serialize(position), userId)`，只按 `IsConnected()` 遍历、排除发信人后直接发送（`NetManager.cs:66-77`），因此也会发给尚未进入世界的客户端；`NetLiquidModule`（`NetLiquidModule.cs:35-74`）按区块打包液体变化，每个区块记录其覆盖坐标，广播前用 `TileSections` 判断该客户端是否加载了对应区块。

### 5. 状态同步策略（服务端广播）
服务端 `remoteClient==-1` 时按消息类型选择广播条件（`NetMessage.cs:1706` 起）：
- 默认：遍历 0..255，发给 `buffer[i].broadcast == true` 且 `IsConnected()` 的客户端；特殊地 msgType==10（区块）额外允许 `State>=3` 的客户端接收（`NetMessage.cs:1815-1826`），这样初始地块能在 `broadcast` 置位前就推给握手中的客户端。
- 23（NPC）：若 NPC 是 boss/城镇 NPC/`netAlways`/已死亡/待生成，则不按区块过滤；否则只发给该 NPC 所在区块处于激活状态的客户端，其余客户端记 `playerNetSyncState[].skippedSyncs`，等区块重新激活时补发（`RecheckSectionsForSkippedUpdates`，`Terraria/NPC.cs:91650`）。
- 27（投射物）：宠物/召唤/重要投射物全量广播；普通投射物同样按区块过滤，被跳过的客户端记在 `netSyncSkippedForPlayer[]`（`NetMessage.cs:1788-1814`），日后补发（`Terraria/Projectile.cs:17356-17365`）。
- 20（区域改动）/ 34、69 / 13（玩家输入回放）：20 用 `SectionRange` 做范围过滤（`NetMessage.cs:1722-1732`）；34/69 走"排除 `ignoreClient` + `broadcast` + `IsConnected()`"（`NetMessage.cs:1710-1721`），与默认分支的差别仅在于不放行 msgType==10 的 `State>=3` 特例；13 有独立分支 `NetMessage.cs:1777-1787`。

**分档与节流**：
- NPC：`UpdateNetworkCode`（`Terraria/NPC.cs:91572`）为 boss 每 5 tick、普通 NPC 每 30 tick 记一次 `netSpam`，积分超过 `netSpamPacketLimit * 间隔` 就推迟到 `netUpdatePendingSpamCooldown`；同时 `StreamUpdatesToNearbyPlayers`（`Terraria/NPC.cs:91623`）按玩家距离（250/500/1000/1500 像素分别 8/4/2/1 分，每满 8 分补发一次）向远处玩家做低帧率更新，这就是 `npcStreamSpeed` 的意义。
- 投射物：只有 `owner == Main.myPlayer` 或 `netUpdate` 置位的才发（`Terraria/Projectile.cs:17326-17346`）；`netSpam < 60` 时发并 +5，否则置 `netUpdate2` 等下一帧，即"最多每 12 帧一条"的软限流。
- 玩家：客户端每 420 tick 无条件补发一次 PlayerControls(13)，每 900 tick 补发生命/区域/传记信息（`Terraria/Main.cs:65458-65474`），保证服务端对玩家状态的最终一致性。

**生成去重**：NPC 在服务端 `NewNPC` 时打 `spawnNeedsSyncing`（`Terraria/NPC.cs:81486`），同帧 `SyncNewlySpawnedNPCs`（`Terraria/NPC.cs:5277-5289`）统一发 23，避免一次生成爆发塞爆发包；`NewNPCInstanceInSlot` 在服务端遇到 `spawnNeedsSyncing` 槽位会先补发一次旧 23（`Terraria/NPC.cs:81425-81430`），并带 `generation` 参数用于区分槽位复用（客户端侧要求 `generation != 0`，`Terraria/NPC.cs:81431-81434`）。

**客户端侧插值与修正**：
- 玩家：收到 13 后不直接瞬移，而是把"旧位置-新位置"差值累加到 `player.netOffset`（`MessageBuffer.cs:1003-1009`），渲染时加回；`UpdateNetOffset`（`Terraria/Player.cs:28936-28967`）把偏移量按 `max(2 像素, 剩余偏移的 10%)` 向 0 收缩（`Player.cs:28943-28966`），并沿偏移方向做一次 `TileCollision` 预演，偏移与速度不共线时按投影距离放大步长，实现"撞墙即停"，从而看起来是"被玩家自己撞停"而不是穿墙；剩余不足 2 像素直接归零。偏移量过大（`multiplayerNPCSmoothingRange`，`MessageBuffer.cs:1006`）直接归零。
- NPC：23 里带了 `SyncAnchor` 锚点修正（不同 NPC 的"位置差"定义不同，`MessageBuffer.cs:1635-1643`），同样平滑；`life` 不直接赋值，而是减去本地"已打出但未确认"的待处理伤害（`NPC.GetPendingDamage`，`MessageBuffer.cs:1668-1671`），避免攻击者的本地预测被服务端旧血量覆盖。

**地块同步的三条粒度**：
1. 整块：`SendSection`（`NetMessage.cs:2733`）把 200×150 的区块按 150 行切条发送 TileSection(10)，发送前把 `TileSections[x,y]` 置位，顺便补发该区块内的城镇 NPC 与箱子内容；`CheckSection`（`RemoteClient.cs:126`）在玩家移动时检测新进入的区块并触发补发（`Terraria/Main.cs:65562-65564` 每帧对每个在线玩家调用）。
2. 小方块：`SendTileSquare`（`NetMessage.cs:2663-2679`）发送 msgType 20，最多 255×255，含位掩码 + 类型 + 帧 + 液体。
3. 单格：msgType 17（`MessageBuffer.cs:1119`），服务端收到后按动作码（0 挖/1 放/2 拆墙/3 放墙/.../18-23 逻辑门与锤击）修改，再广播给 `ignoreClient` 以外的客户端（`MessageBuffer.cs:1283-1288`）；服务端同样用 `SpamDeleteBlock/SpamAddBlock` 记分反作弊（`MessageBuffer.cs:1135-1148`）。

### 6. 反作弊与流控
- 单连接发送在途计数 `spamCount` 在 `SendPacket` 中 +1、在写完成回调中 -1（`NetMessage.cs:1869`、`RemoteClient.cs:251-254`、`RemoteServer.cs:51-54`），用于诊断 UI 与限流。
- `SpamUpdate`（`RemoteClient.cs:70-116`）每 tick 检查四类刷屏积分，超阈值 `BootPlayer`；积分随时间线性衰减。
- 超时：客户端与服务端都是每 tick `TimeOutTimer++`，超过 7200（约 2 分钟）断开（`Terraria/Main.cs:65485-65490`、`Terraria/Main.cs:65551-65563`）；握手未完成（`State==0`）时计数 +3 加速淘汰。
- 所有报文按 `GetData` 里 `Main.ActiveNetDiagnosticsUI.CountReadMessage` / `CountSentMessage` 打点（`MessageBuffer.cs:142`、`NetMessage.cs:1870`），供诊断面板统计。

### 7. Steam 平台接入
- 选型：`SocialAPI.Initialize`（`Terraria.Social/SocialAPI.cs:33-63`）默认走 Steam；专服只有带 `-steam` 启动参数才启用 Steam，否则只开 TCP。`LoadSteam`（`SocialAPI.cs:88-110`）按是否为专服选择 `NetServerSocialModule` 或 `NetClientSocialModule`。
- 通道：`NetSocialModule` 定义两个 P2P 通道——服务端读通道 1、客户端读通道 2（`Terraria.Social.Steam/NetSocialModule.cs:23-25`），双向都用各自的读通道收、写通道发，避免收/发彼此阻塞。
- 收：`SteamP2PReader.ReadTick`（`SteamP2PReader.cs:88-132`）由 `CoreSocialModule.OnTick` 驱动（`NetSocialModule.cs:55-59`），不断 `IsP2PPacketAvailable`/`ReadP2PPacket`，从 4096 字节缓冲池（`BUFFER_SIZE = 4096`，`SteamP2PReader.cs:30`）取缓冲，把包放进"每个 SteamID 一个队列"；被 `OnReadEvent` 判为无效的包会立即把缓冲还回池（`SteamP2PReader.cs:126-129`）。
- 发：`SteamP2PWriter.QueueSend`（`SteamP2PWriter.cs:31-59`）把小包拼进 1024 字节缓冲，`SendAll`（`SteamP2PWriter.cs:61-83`）在一个 tick 里统一 `SendP2PPacket`（可靠模式 `EP2PSend=2`），这就是 Steam 侧的"批量发送"。`SocialSocket.AsyncSend` 只是把数据 `QueueSend` 后立刻回调（`Terraria.Net.Sockets/SocialSocket.cs:36-42`），因而上层 `SendData` 语义与 TCP 一致。
- 鉴权：客户端 `SendAuthTicket`（`NetClientSocialModule.cs:233-262`）构造 `[uint16 长度][byte 93][票据]`，用通道 1 直接 `SendP2PPacket`；服务端阅读过滤器（`NetServerSocialModule.cs:193-234`）识别 `data[2]==93`，调用 `SteamUser.BeginAuthSession`，结果码 0 才把状态置 `Connected` 并广播用户列表。
- 好友限制：`ShouldBlockAsNotFriends`（`NetServerSocialModule.cs:274-283`）在非 FriendsOfFriends 模式下只接受 Steam 好友或自己；`MessageBuffer.cs:187-192` 在收到 Hello 时先检查这条，被拦下会回 Kick(2) 并附 `Net.SteamHostOnlyAllowsFriends`。
- 大厅：加入流程通过 `LobbyChatMsg_t` 回调处理，房主用聊天室消息广播"请 SetPlayedWith"，让 Steam 好友面板正确显示同局玩家（`NetSocialModule.cs:85-113`）。

### 8. 区块尺寸约定
区块尺寸是写死的：`GetSectionX/Y`（`Netplay.cs:770-778`）按 200（X）/150（Y）划分，`RemoteClient.TileSections` 的维度也用 `Main.maxTilesX/200+1` × `Main.maxTilesY/150+1`（`RemoteClient.cs:31`）与之对应。`SendSection` 内把区块按 150 行切条（`NetMessage.cs:2737-2751`），`ResyncTiles`（`NetMessage.cs:2719-2731`）也复用这个网格做"局部强制重传"。

## 设计要点与取舍

1. **"手写万能参数"而不是反射/结构化序列化**。`SendData` 只有 7 个数字槽位 + 1 个文字，靠 `switch` 手写每条消息的读写顺序。代价是增加一个协议要同时改 `SendData` 的写分支和 `MessageBuffer.GetData` 的读分支，极易两边不一致；收益是零分配、可精确控制字节宽度（大量字段压成 `BitsByte` 或 `byte`）。
2. **长度前缀 + 逐条对齐**。`CheckBytes` 强制把读取位置拨到"本条起点+长度"，即使某分支少读/多读也不会破坏后续报文——这是后向兼容的隐性基础：旧客户端读不懂的新报文可以被"整条跳过"而不是流错位（但会触发异常日志）。
3. **服务端权威、客户端算输入**。玩家 13 号报文只有按键位、位置、速度、朝向、坐骑等少量字段（`NetMessage.cs:449-517`），客户端并不上传"我打出了多少伤害"，`DamageNPC(28)` 交给服务端判定再回 `DamageNPCAck(162)`。代价是延迟感必须靠客户端预测 + `netOffset` 平滑掩盖；收益是防篡改。
4. **按区块做视野裁剪的广播**。23/27/20 都依赖 `IsSectionActive`；`SectionInactiveTime=60`（约 1 秒）的宽限期避免边界抖动导致频繁补发，被跳过的事件用 `skippedSyncs` / `netSyncSkippedForPlayer` 消费，保证"进视野立即补"。
5. **两条发送路径并存**。旧路径简单直接但状态耦合严重；新 `NetModule` 路径让液体、文字、Ping、Bestiary 等子系统自带编解码、独立演进，并天然支持"单机 loopback"。两者共用同一个 `ISocket` 与长度前缀，可在同一连接上混合使用。
6. **节流不是丢包而是延迟**。NPC 的 `netSpam` 与投射物的 `netUpdate2` 都是"攒积分 → 等积分下降 → 补发"，而不是直接丢弃更新；配合 `RecheckSectionsForSkippedUpdates` 实现最终一致。
7. **线程模型是"IO 在后台、逻辑在主线程"**。Socket 的 `AsyncReceive` 回调只做 `BlockCopy` 入缓冲（加 `lock`），真正的 `GetData` 在主线程逐帧处理；发送则在调用点同步序列化 + `AsyncSend`。服务端有独立的连接管理线程 `ServerLoop`（`Netplay.cs:287-297`），每轮调 `UpdateConnectedClients`（内部遍历 256 槽位做 `RemoteClient.Update` → `TryRead` → `AsyncReceive`）并在 Udp 上做局域网广播（`StartBroadCasting` / `StopBroadCasting`）；超时计数与断线判定不在该线程，而在主线程 `UpdateServer` 中完成（`Main.cs:65550-65568`）。
8. **平台抽象靠 `SocialSocket` 抹平**。Steam P2P 是"消息导向"而 TCP 是"字节流"，`SocialSocket.ReadCallback`（`SocialSocket.cs:44-51`）用"收不到就 Sleep(1) 重试"把两者统一成流语义，简单但不优雅；对零拷贝或超大包不友好。
9. **协议版本号硬编码**。Hello 里的 `"Terraria" + 326` 是唯一版本标识，没有协商机制——版本不一致直接被踢回菜单。
