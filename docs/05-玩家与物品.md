# 玩家、物品与合成

## 一句话结论

Terraria 的"玩"这一层被压缩成一个巨型函数 Player.Update：它每帧先把玩家身上所有"可被装备/增益改写"的数值重置回基准，再依次把增益、装备、坐骑、饰品奖励叠加回来，然后用一份"输入 → 加速度 → 分步碰撞 → 位置"的确定性物理积分把玩家推到新位置，最后交给 ItemCheck 处理手持物品的"起手/生效/冷却"三段式计时。物品的 5 万个字段里真正驱动这一层的只有 useTime（生效间隔）、useAnimation（挥动动画长度）、reuseDelay（收手延迟）三个整数和 useStyle/shoot/useAmmo 等路由字段；合成则是一张预烘焙的"配方 × 需求 → 物品数量"查表问题，靠一个 _ownedItems 字典把背包、宝箱、虚空袋和 RecipeGroup 假物品计数摊平成一维占用表，再用 HowManyTimesCanRecipeBeCrafted 做整除判定。

## 关键数据结构

### Player：数值分层而非字段直改

Player 的字段大致分三层【Terraria/Player.cs:24542】：

- 本帧瞬时量：position / velocity / itemAnimation / itemTime，每帧被物理与 ItemCheck 改写。
- 本帧累计量：maxRunSpeed、accRunSpeed、jumpSpeed、statDefense、meleeDamage、moveSpeed 等，由 ResetEffects 起手回到基准，之后被增益和装备做加法/乘法叠加。
- 持久状态：inventory[58]、armor[20]、buffType/buffTime。

Update 的第一段显式给出"基准值"——gravity 取 defaultGravity、jumpHeight=15、jumpSpeed=5.01、maxRunSpeed=originalRunSpeed、runAcceleration=0.08、runSlowdown=0.2——见【Terraria/Player.cs:24556】。这一点决定了整套装备系统是"重算式"而非"增量式"：任何一件装备被摘下，下一帧基准值自然恢复，不需要反算。

增益槽位固定 44 个（maxBuffs），用两个平行数组 buffType[] 与 buffTime[] 表示【Terraria/Player.cs:1491】【Terraria/Player.cs:1493】【Terraria/Player.cs:1495】。这种"平行数组 + 固定容量"的写法在光照、投射物、NPC 中复用，是停用对象池的常见做法。

### Item：字段即配置表

Item 的核心使用字段集中在基类字段区【Terraria/Item.cs:145-159】【Terraria/Item.cs:185-189】【Terraria/Item.cs:245】【Terraria/Item.cs:253】【Terraria/Item.cs:261】【Terraria/Item.cs:267】【Terraria/Item.cs:317】：

| 字段 | 行号 | 工程含义 |
|---|---|---|
| useStyle | Item.cs:147 | 渲染/命中盒分派：0 无动画、5 手持枪类、剑类等 |
| useTime | Item.cs:155 | 两次"生效"之间的帧间隔 |
| useAnimation | Item.cs:153 | 一次挥动的总帧数，通常 ≥ useTime |
| reuseDelay | Item.cs:317 | 动画结束后额外锁定的帧数，用于长前摇/后摇 |
| channel | Item.cs:149 | 按住持续生效（连射/蓄力），由 StartChanneling 打开 |
| autoReuse | Item.cs:187 | 按住即自动再次触发 |
| shootsEveryUse | Item.cs:293 | 每帧都可发射，不受 itemTime 节流 |
| shoot / useAmmo | Item.cs:245 / Item.cs:253 | 发射的投射物 ID / 要求的弹药类别 |

useTime 与 useAnimation 分离是这套模型的要点：动画长度决定"看起来挥多久"，itemTime 决定"多久后才能再次造成效果"。两者解耦后可以实现"动画短、冷却长"（大锤）或"动画长、冷却短"（多段挥击）。

### Recipe：预烘焙的一维占用表

配方不存储"物品列表"，而是存储一个"需求槽 → 键"的映射【Terraria/Recipe.cs:13-44】。RequiredItemEntry 只有两个字段：itemIdOrRecipeGroup 与 stack；当 itemIdOrRecipeGroup ≥ RecipeGroup.FakeItemIdOffset（1000000）时，这个键代表一个配方组而不是具体物品【Terraria/Recipe.cs:17-23】【Terraria/RecipeGroup.cs:11】。FakeItemIdOffset 的意义是：让"木头"这类组在同一个字典里拥有一个不会与真实 ItemID 冲突的伪 ID。

配方本身的上限：maxRequirements = 15、maxRecipes = 3700【Terraria/Recipe.cs:56-60】；环境条件被展开为一组布尔字段 requiredTile、needHoney、needWater、needLava、needSnowBiome、needGraveyardBiome、needTorchGodsFavor、alchemy【Terraria/Recipe.cs:72-96】。

### RecipeGroup：伪物品的聚合

RecipeGroup 的内部是 HashSet 与 List 双写——ValidItems 做 O(1) 包含判断，Items 保序用于取占位物品与排序【Terraria/RecipeGroup.cs:15-21】。每个组在注册时拿到自增的 RegisteredId，对外以 RegisteredId + FakeItemIdOffset 暴露成"假物品 ID"【Terraria/RecipeGroup.cs:83-95】。CountUsableItems 在合成时把组内所有成员的数量累加起来【Terraria/RecipeGroup.cs:97-107】，这就是"任意木材都算木头"的全部实现。

### Chest

Chest 是一个定长数组容器：maxItems 默认 40（DefaultMaxItems），理论上限 200【Terraria/Chest.cs:60-62】【Terraria/Chest.cs:66】。bankChest 标记它是否是"个人存储"（猪猪银行、虚空袋等），CanStack 与配方收集对它区别对待。全局用 _chestsByCoords（坐标→箱子）与 _chestInUse（占用集合）两张表管理【Terraria/Chest.cs:86-90】。

## 执行流程

### 1. Player.Update 的宏观顺序

按源码顺序，单帧内发生的事是：

1. 输入与外设：Main.myPlayer 上更新 LockOnHelper，处理"待处理的背包操作"时锁死地块交互【Terraria/Player.cs:24544-24553】。
2. 基准数值与重力特例：先写回基准值，再按 shimmer / 水 / 蜂蜜 / 鱼鳃 / 三叉戟覆盖 gravity、maxFallSpeed、jumpHeight【Terraria/Player.cs:24556-24616】。
3. 无敌帧与各类计时器递减【Terraria/Player.cs:25651】。
4. ResetEffects()：把所有装备/增益可改写的变量回到"无任何加成"的状态【Terraria/Player.cs:25686】。
5. UpdateBuffs(i)：遍历 44 个增益槽，递减时间，并把每个增益的效果写进上述变量【Terraria/Player.cs:25761】。
6. UpdateEquips(i)：遍历背包与前 10 个装甲/饰品槽，应用护甲、前缀与饰品奖励【Terraria/Player.cs:25828】。
7. UpdateArmorSets(i)：处理"成套才生效"的套装收益【Terraria/Player.cs:25880】。
8. UpdateLifeRegen / UpdateManaRegen / UpdateJumpHeight：把前面累计的属性换算成每帧回复与跳跃参数【Terraria/Player.cs:26175】【Terraria/Player.cs:26193】【Terraria/Player.cs:26209】。
9. 物理积分与碰撞分派（详见第 2 节）。
10. ItemCheckWrapped(i) → ItemCheck()：处理手持物品【Terraria/Player.cs:28493】【Terraria/Player.cs:32031】。
11. PlayerFrame()、护甲/生命上限裁剪、抓钩重置、阴影更新【Terraria/Player.cs:28494-28514】。

关键设计是第 4~7 步严格串行而非并行：ResetEffects 是唯一的"清零"，其余都是"叠加"，因此任何写 statDefense 的增益都在护甲之后仍能被乘除类增益处理。源码中可以直接看到 brokenArmor / witheredArmor 在增益与装备都算完之后才做 statDefense /= 2【Terraria/Player.cs:26217-26224】。

### 2. 输入 → 物理 → 状态

水平输入的处理入口是 HorizontalMovement()【Terraria/Player.cs:19897】，它在 Update 内被调用一次【Terraria/Player.cs:26887】。该函数读 controlLeft / controlRight 两个布尔，维护一个"当前速度是否已达到奔跑阈值（(accRunSpeed+maxRunSpeed)/2）"的判断，并在不同地面状态下给出不同的加速度。

垂直方向不走统一积分，而是按介质分派：

- 干地：DryCollision(fallThrough, ignorePlats)【Terraria/Player.cs:23684】。
- 水中：WetCollision(fallThrough, ignorePlats, 速率)，湿身（水/岩浆）取 0.5（lavaWet 时取 num114，否则 num113，两者均为 0.5f），微光湿身 shimmerWet 取 0.375（num115），蜂蜜湿身取 movementSpeed=0.25【Terraria/Player.cs:28376-28398】。
- 被舌卷（tongued）或处于微光凝固态（shimmering）时直接 position += velocity（微光态额外 ×0.375），跳过碰撞【Terraria/Player.cs:28381-28389】。

DryCollision 本身是一个"按 16 像素（且不超过自身 hitbox）切片"的循环：把本帧位移拆成不超过 val 的小段，每段依次做重力下落、台阶上/下自动跨越（Collision.StepUp / StepDown）、瓦片碰撞（TileCollision）、斜坡行走（WalkDownSlope）、传送带、再合并【Terraria/Player.cs:23684-23735】。这样分段的目的是防止一帧的大位移穿墙；切片长度 val 取 16、width-0.5、height-0.5 三者的最小值【Terraria/Player.cs:23686-23688】，即单步不超过 16 像素，且不超过角色自身宽高（角色越小 val 越小），以免一步越过碰撞体。

碰撞分派在 Update 主体中写成一段 if/else 瀑布【Terraria/Player.cs:28372-28432】：vortexDebuff 先改写 velocity.Y，然后 tongued / shimmering / shimmerWet / honeyWet / wet / 干地依次判定，另有史莱姆坐骑、矿车、下砸三种情况的"先只走 Y 再走 X"补算。这类"分介质 if 链"是横版游戏物理常见写法，代价是介质组合时优先级难以表达（源码靠顺序而非显式状态机）。

落地状态的收尾：velocity.Y==0 且不在抓钩状态时调 FloorVisuals，然后 SwitchTiles 处理开关块，再更新压力板位置【Terraria/Player.cs:28476-28484】。

### 3. 装备与增益

ResetEffects 的职责不仅是"清零"，还承担跨帧衰减逻辑：rapidAttackBonus 每帧 -0.005 直到 0，微光透明度按帧逼近 0.8【Terraria/Player.cs:18389-18422】。这一点说明部分"临时强化"是通过在 ResetEffects 里做衰减、随后在 UpdateEquips 里重加来实现的。

UpdateBuffs 的循环体是三段式：递减 buffTime → 若该增益属于坐骑类则 SetMount 并把 buffTime 钉死在 10（坐骑不会因计时耗尽而消失，靠卸载坐骑来解除）→ 否则按 buffType 做效果分派【Terraria/Player.cs:9942-10010】。钉死 10 帧是"无限期增益"的常见手法：只要坐骑在，每帧都会被续命。

AddBuff(type, time) 是增益写入的唯一入口，顺序固定为：无敌/免疫检查 → 非本地玩家的 PvP 增益走 NetMessage 55 → 若新增益属于"进食状态"则先清除同类 → 时长判定（AddBuff_DetermineBuffTimeToAdd）→ 尝试延长已有同类 → 否则移除冲突的宠物/近战增益、削减相关增益时长、最终写入【Terraria/Player.cs:5255-5285】。这种"先查重再覆盖"的顺序保证了同类增益只占一个槽，且不会因为重复施加而叠加时长。

UpdateEquips 的骨架对工程最有参考价值：先遍历背包 58 格刷新"信息类/机械类"饰品（因为它们放在背包里也生效），再遍历 10 个装甲/饰品槽，逐件检查 (a) 是否解锁 (b) 是否专家专属且当前非专家 (c) 槽位与物品类型是否匹配，通过后才执行 GrantPrefixBenefits（前缀加成）与 GrantArmorBenefits（物品自身加成）【Terraria/Player.cs:12987-13020】【Terraria/Player.cs:12964-12985】。槽位匹配规则写死在 UpdateEquips_CanItemGrantBenefits：0/1/2 号槽要求 headSlot/bodySlot/legSlot ≥ 0，3~9 号槽要求 accessory【Terraria/Player.cs:12964-12985】。

两个加成函数的切分点很清晰：GrantArmorBenefits 处理物品自身属性（防御、生命回复、移动速度等，statDefense += armorPiece.defense）【Terraria/Player.cs:13201-13220】，GrantPrefixBenefits 专门处理 62~67 等前缀带来的固定数值（如 62 号前缀 +1 防御、66 号前缀 +20 最大法力）【Terraria/Player.cs:14052-14074】。把前缀从物品属性里剥离出来，是为了让附魔在不修改 Item 基础数据的前提下改变数值。

### 4. Item 使用流程：起手 / 生效 / 冷却

ItemCheck 是整段系统的核心，入口在【Terraria/Player.cs:42917】。它的骨架可以概括为：

- 若玩家被控制（CCed），直接清零动画并返回【Terraria/Player.cs:42921-42926】。
- 取当前选中物品，处理"快速使用"、光标图标（鱼饵/弹药预览）等 UI 附属逻辑【Terraria/Player.cs:42929-42972】。
- ItemCheck_AutoReuseLogic：若物品 autoReuse，则在动画走到最后 1 帧时强制把 releaseUseItem 置真，从而"等效于玩家松手再按"【Terraria/Player.cs:53519-53537】。
- 递减 itemAnimation；归零时若 reuseDelay 非零则通过 ApplyReuseDelay 把 itemAnimation 与 itemTime 一并设成 reuseDelay【Terraria/Player.cs:43071-43085】【Terraria/Player.cs:53422-53428】。
- 递减 itemTime。
- 动画仍在进行且 itemTime 已归零时，执行物品的"帧内效果"并再次 ApplyItemTime / ApplyItemAnimation【Terraria/Player.cs:43158-43220】。

计时器三件套的赋值关系是：

| 方法 | 作用 | 关键行 |
|---|---|---|
| ApplyItemTime(item) | itemTime = item.useTime | Player.cs:4401-4404 |
| SetItemTime(frames) | itemTime = itemTimeMax = frames（仅冷却，不动动画） | Player.cs:4391-4400 |
| ApplyItemAnimation(item) | 按 useStyle 与物品类别决定 itemAnimationMax，并乘上速度加成 | Player.cs:4448-4479 |

ApplyItemAnimation 里的分支揭示了"动画长度受什么影响"：近战物品乘以 meleeSpeed（除非 NoMeleeSpeedBonus）、召唤类乘以召唤攻速、放置方块乘以 tileSpeed、放墙乘以 wallSpeed，其余直接用 useAnimation【Terraria/Player.cs:4453-4479】。也就是说，攻速加成的实现是"缩短动画"，而不是"缩短冷却"，冷却仍由 useTime 原值决定。

真正"生效"的分派点在 ItemCheck 的后半段：sItem.shoot > 0 且满足"动画进行中 + itemTime 归零 + 允许攻击"时调用 ItemCheck_Shoot【Terraria/Player.cs:43893-43900】。ItemCheck_Shoot 内部先取 sItem.damage / shootSpeed，射击类武器先走 PickAmmo 换算出实际投射物与伤害，再创建投射物【Terraria/Player.cs:47459-47480】。GetWeaponDamage 只是 damage × GetWeaponDamageMultiplier() 的封装，没有额外逻辑【Terraria/Player.cs:54064-54071】。

非射击类物品走各自的专用分支：导线工具 ItemCheck_UseWiringTools 要求 itemAnimation > 0 且 ItemTimeIsZero 才允许放置，成功后 ApplyItemTime【Terraria/Player.cs:47152-47182】；除草机、水桶、乐器、彩纸等各自独立【Terraria/Player.cs:43894-43896】。治疗/增益类物品则在 ItemCheck 中直接检查 item.healLife / buffType，先施加效果再 ApplyItemTime【Terraria/Player.cs:43185-43200】。

"起手"由 ItemCheck_StartActualUse 完成：设置攻击方向、StartChanneling、attackCD=0、ApplyItemAnimation，并在需要时播放使用音效【Terraria/Player.cs:52291-52315】。把"设为动画长度"放在起手、把"设为冷却长度"放在生效，是这套三段式的关键——一个大锤可以动画演出 30 帧，但只在第 12 帧设 itemTime，之后的 18 帧只是演出。

### 5. 配方匹配

配方匹配不是"遍历要求去背包找"，而是被摊平成一次字典计数 + 若干次整除：

1. 清空 _ownedItems，收集玩家背包前 58 格【Terraria/Recipe.cs:366-372】。
2. 收集容器：当前打开的箱子、虚空袋（useVoidBag 且当前不是虚空袋），以及设置开启"从附近箱子合成"时的 NearbyChests 中所有范围内容器（排除被锁或被占用的）【Terraria/Recipe.cs:375-405】。
3. CollectItems 把同一 ItemID 的 stack 累加进字典【Terraria/Recipe.cs:418-431】。
4. AddFakeCountsForItemGroups：对每个 RecipeGroup 计算 CountUsableItems，写入伪 ID 键【Terraria/Recipe.cs:409-416】【Terraria/RecipeGroup.cs:97-107】。
5. 遍历所有 3700 条配方：环境条件 PlayerMeetsEnvironmentConditions 且 CollectedEnoughItemsToCraft 通过则加入可用列表【Terraria/Recipe.cs:230-259】。

第 5 步的两个判定都值得看细节。CollectedEnoughItemsToCraft 委托给 HowManyTimesCanRecipeBeCrafted，后者对每个需求槽做 value / stack 取最小值，任一缺失立刻返回 0【Terraria/Recipe.cs:275-311】。环境条件则是逐项短路的布尔与：requiredTile 必须在 player.adjTile 里为真（即玩家站在工作台等方块旁）、浇水/蜂蜜/岩浆/雪地/墓地/火把神各查对应玩家状态【Terraria/Recipe.cs:322-355】。

配方的"需求槽是组"这件事在性能上是预处理的：CreateRequiredItemQuickLookups 在初始化时把每条配方的 requiredItem[] 转成 requiredItemQuickLookup[]，若某需求的物品属于该配方 acceptedGroups 中的某组，就把键替换成该组的伪 ID【Terraria/Recipe.cs:15162-15190】。于是运行时匹配完全不需要再理解"组"，只需要 _ownedItems 里存在这个键。这是"编译期（加载期）预处理换运行期简单性"的典型做法。

GetIngredientsForOneCraft 在真正消耗时把 quickLookup 复制并扣除炼金桌折扣：若配方 alchemy 且玩家在炼金桌旁，则每 3 份材料有 1 份免掉（Main.rand.Next(3)==0 计数扣除）【Terraria/Recipe.cs:196-228】。注意这里用的是未定种子随机，所以折扣按每次合成独立掷骰。

### 6. 箱子与商店

Chest 的世界内操作（放置、解锁、销毁）与存储本身解耦：箱子按坐标在 _chestsByCoords 索引，FindChest 通过坐标反查【Terraria/Chest.cs:507-515】；配方收集时用 IsLockedOrInUse 排除被玩家占用或上锁的箱子【Terraria/Chest.cs:172-183】。

商店复用 Chest 结构（CreateShop 返回一个 bankChest=false 的箱子），但商品的生成是 SetupShop(type) 中的巨型 switch：对每个 NPC 类型把固定条目 SetDefaults 依次写入数组【Terraria/Chest.cs:1354 起】。卖回给商店的商品走 AddItemToShop：先从 shopSellbackHelper 扣除数量（最近售出的同款物品），剩余部分以 buyOnce=true 新开一格【Terraria/Chest.cs:664-700】。

价格计算全在 Player.GetItemExpectedPrice【Terraria/Player.cs:35634-35672】：

- 先取 item.GetStoreValue() 作为卖出/买入基准。
- 若有折扣（discountAvailable，来自装备的 discountEquipped，在 Update 中仅当不在商店时同步）【Terraria/Player.cs:25831-25834】，对非 buyOnce 物品买入价 ×0.8，若本身是商店商品则卖出价也跟进。
- 再乘除 currentShoppingSettings.PriceAdjustment：buyOnce（稀有商品）的买入价除以该系数，普通商品乘以它、卖出价除以它——即幸福度系数对普通商品同时抬高买价、压低卖价。
- buyOnce 物品最终再 /5，作为"回购价"。

currentShoppingSettings 在 SetTalkNPC 时刷新：talkNPC == -1 时用 NotInShop 常量，否则问 Main.ShopHelper【Terraria/Player.cs:4360-4376】。SellItem 的实际出售价是 calcForSelling/5（至少 1），若该物品曾被本店卖出过（shopSellbackHelper.GetAmount > 0），差额部分按 calcForBuying 补回【Terraria/Player.cs:35443-35466】。

### 7. 重铸

重铸是一行核心逻辑加一段演出：ReforgeItemInReforgeSlot 先 ResetPrefix()，再对物品调用 Prefix(-2, out rolledPrefixIsTopTier)，并根据布尔值播放"最佳重铸"音效与粒子、设置 60 帧冷却【Terraria/Main.cs:42615-42647】。ResetPrefix 只是把 prefix 设 0 并 Refresh，让物品回到无前缀的基础值【Terraria/Item.cs:49941-49951】。

Item.Prefix 的参数 -2 表示"强制掷出一个非空前缀"：内部先 BestPrefixValue() 取得当前物品理论上限作为比较基准，然后进入 while 循环反复掷 —— 若 prefixWeWant == -2 且掷出 0 号（空）前缀则认为失败重掷；TryGetPrefixStatMultipliersForItem 失败也重掷【Terraria/Item.cs:505-563】。具体掷法在 RollAPrefix：从 GetRollablePrefixes() 里均匀随机取一个【Terraria/Item.cs:1140-1148】。

另一条不显眼的规则：当 prefixWeWant == -1（普通自然掉落前缀）时，若随机数命中 1/4 则直接给空前缀；若掷中的前缀属于 ReducedNaturalChance 集合，则又有 2/3 概率被降为空前缀【Terraria/Item.cs:543-557】。这解释了为何怪物掉落的高价值前缀比"随机重铸"更难遇到——两者走的是同一函数的不同参数。

## 设计要点与取舍

**重算式属性面板。** 每帧 ResetEffects + 全量重扫 58 格背包与 10 个装备槽，复杂度是 O(68) 每次属性访问的常数级重算。代价是每帧几十次小循环的开销，收益是任何"动态出现/消失的加成"（例如饥饿、微光、套装、传奇前缀）都不需要写"扣除"分支，也就不可能出现加成残留这类状态不一致。相比事件驱动的增量属性系统，它在多人/单人、存档读入、装备切换等多种入口下都天然自洽。

**动画与冷却解耦。** useAnimation 决定视听表现，useTime 决定实际节奏，两者通过 itemTime 串在一起。好处是同一个武器可以有完全不同的手感组合；坏处是从数据上无法一眼看出"这个武器每秒打几下"——必须同时读三个字段并考虑 ApplyItemAnimation 里的攻速乘法。

**自动复用 = 模拟松手。** ItemCheck_AutoReuseLogic 不另写一套"持续按住"逻辑，而是在动画最后一帧把 releaseUseItem 置真【Terraria/Player.cs:53519-53537】。这让 autoReuse 与"玩家真的快速点按"共用同一条判定，网络同步（其他玩家用控制位上报）也能一致。副作用是部分依赖 releaseUseItem 的物品（例如松手才发射的 ShootOnUseRelease 集合）需要额外排除【Terraria/Player.cs:43851-43855】。

**配方组用伪 ID 统一到同一张表。** 若不这样做，每个需求槽都要写"若是组，遍历组内所有成员去背包找"的分支，且数量分摊（一组里放了 3 块不同类型木头）需要额外算法。伪 ID 把组变成"另一种物品"，计数、整除、消耗三处代码都无需知道组的存在，只在构建 quickLookup 与累加假计数时各处理一次。

**预烘焙 quickLookup。** 3700 条配方 × 15 个需求槽若每次都在运行时判断归属，结合"每帧刷新列表"就是 5.5 万次集合包含操作。CreateRequiredItemQuickLookups 在加载期做完替换后，运行时每次只有整数除法与字典查找。

**箱子计价与配方收集的共享抽象。** Chest 同时承担世界容器、NPC 商店、个人银行三种角色，只靠 bankChest 与 index 区分。这省掉了一套独立的 Shop 类型，但也导致商店相关字段（buyOnce、isAShopItem）与容器字段混在同一结构上，可读性因此受损。

**商店价格的单向折扣。** 幸福度系数对普通商品是"买价乘、卖价除"，即玩家在任何情况下都是双输的方向；只有自己的装备折扣（discountAvailable）会真正降低买价。这一"不可被幸福度反超"的设计避免了玩家通过刷幸福度把 NPC 变成套利机器。

**重铸与自然前缀共用同一掷骰函数但参数不同。** Prefix(-2) 会拒绝空前缀重掷，Prefix(-1) 会主动放弃部分前缀。这比"两套随机表"更省数据，但使得数据驱动的概率调整（比如让某个前缀更稀有）必须在函数里加集合判断，而不能只改权重表。

**未验证项。** CraftingRequests 类（负责真正扣料与发放成品）定义在 Terraria.GameContent/CraftingRequests.cs，只在 Recipe.cs:372、Player.cs:55586 等处被引用；Main.CraftItem_GrantItem 存在，但调用链上如何从配方跳到扣料未能完整确认，此处标注未验证。Main.ShopHelper 定义在 Terraria.GameContent/ShopHelper.cs（Main 字段声明于 Main.cs:1889），Player.cs:4374 的 Main.ShopHelper.GetShoppingSettings 调用可解析。

### 8. 输入采样与本地/远端玩家的分叉

Update 在很靠前的位置就把"谁在操作"这件事处理掉了：Main.myPlayer == i 的玩家会设置 autoReuseAllWeapons（来自设置项）、重置地块预览、处理快速抓钩冷却；其他玩家则走"出界检测"路径，用 position 换算成瓦片坐标并用 WorldGen.InWorld 判断是否越界，越界即置 outOfRange【Terraria/Player.cs:24646】【Terraria/Player.cs:24722】。

本地玩家的输入不是直接读键盘，而是 PlayerInput.Triggers.Current.CopyInto(this) 把抽象的按键触发状态拷进 controlLeft/controlRight/controlUp/controlJump 等布尔字段【Terraria/Player.cs:24962】。这一层抽象让键盘、手柄、触屏共用同一套 control* 字段，物理与物品逻辑完全不需要知道输入设备。随后代码对若干交互场景做消歧：左右同时按下时取消左键、在背包/设置窗口打开时屏蔽移动、聊天输入时只允许部分触发【Terraria/Player.cs:24962-25160】。最后把 controlLeft 与 controlRight 在"方向反转"状态下交换，这也是为什么重力药水翻转后左右输入语义保持一致【Terraria/Player.cs:25192-25202】。

远程玩家则完全不做输入采样，只消费网络下发的 control* 位与位置，这正是多人同步能保持一致的根因：服务器与客户端执行的是同一份确定性物理代码，输入位只是它的输入参数。

### 9. 物品槽位布局

理解 ItemCheck 与合成之前需要先记住槽位编号约定：

- 0~49 号：背包主体热区（含 0~9 快捷栏）。
- 50~53 号：备用背包。
- 54~57 号：钱币槽（BuyItem 中 CoinsCount 正是扫描 54~57 与 58 以外的空位）【Terraria/Player.cs:35682】。
- 58 号：鼠标手持格（Main.mouseItem 的映射），因此 CollectItems(player.inventory, 58) 恰好排除它【Terraria/Recipe.cs:368】。

armor 数组则有 20 格：0~2 是头/身/腿，3~9 是可解锁的饰品槽（含专家恶魔之心与大师模式额外槽），10 起是时装槽。GetEffectiveArmor(slot) 把"实际生效的槽"抽象出来，让时装与效果槽的切换对 UpdateEquips 透明【Terraria/Player.cs:5678-5681】。

### 10. 弹药与消耗

HasAmmo 只做一件事：当物品 useAmmo > 0 时，扫描背包 58 格找 ammo 字段匹配的格子，找到即认为可用【Terraria/Player.cs:54074-54090】。真正的"选谁"在 PickAmmo：它先从特定发射器-弹药匹配表里找专用投射物，找不到再走通用映射，并把弹药物品 ID 通过 out 参数带出供消耗【Terraria/Player.cs:54093-54101】。这意味着"用不同的箭打出不同效果"完全由数据表驱动，ItemCheck_Shoot 只负责把结果转成投射物。

值得注意的是 ItemCheck 中的光标图标预览提前做了同样的扫描，只是把结果画在鼠标旁而不是消耗——同一判断写两处，是"UI 预览"与"实际消耗"分离带来的重复成本【Terraria/Player.cs:42934-42972】。
