# 00 · 总览：从二进制到可读懂的游戏

本仓库把 Terraria **v1.4.5.8** 的托管程序集反编译成约 80 万行 C#，并按子系统拆解其实现原理。
本页给你三样东西：一张全局架构图、一条推荐阅读路线、一份"读反编译码"的心法。

---

## 一句话结论

Terraria 是一个**以全局单例 `Main` 为中心、以数组为实体容器、以巨型 `switch` 为 AI 分派**的
2D 沙盒游戏。它没有用 ECS，也没有用现成的 UI/渲染框架，几乎所有子系统都通过静态字段互相可达。
理解它的关键，是先认清这条主干：**`Main` 驱动一切，`NPC`/`Projectile`/`Player` 是大数组，行为分派靠类型分支**。

## 二进制基本情况

| 项 | 值 | 依据 |
| :--- | :--- | :--- |
| 游戏版本 | `v1.4.5.8` | `Terraria/Main.cs:320`（`versionNumber`） |
| 运行时 | .NET Framework 4.0（Mono/托管） | `Terraria.exe` 的 PE 头（`Mono/.Net assembly`） |
| 图形/音频层 | FNA 26.3.0.0（XNA4 兼容层） | 程序集引用表 |
| 是否混淆 | **否**，类名/方法名/字段名完整保留 | 可直接列出 2235 个类型 |
| 源码规模 | 客户端 1549 个 `.cs`，约 79.6 万行 | `find ... | wc -l` |

因为没有混淆，这份源码的**命名是可信的**——`AI_000_TransformBoundNPC` 这种方法名就是作者自己写的。
真正丢失的只有**局部变量名**（IL 里本来就没有），它们被还原成 `num3`、`flag2`、`val`。

## 全局架构

### 启动链

```
Program.Main                      Terraria/Program.cs:221-232
 ├─ new Main()                    整个游戏的单例，构造在 Main.cs
 ├─ Lang.InitializeLegacyLocalization()
 ├─ SocialAPI.Initialize()        平台接入（Steam / WeGame）
 ├─ LaunchInitializer.LoadParameters(main)   解析启动参数
 ├─ Main.dedServ ? main.DedServ() : main.Run()   ← FNA Game.Run()
 └─ Main.Run → FNA 主循环
      ├─ Initialize()             Terraria/Main.cs:6591
      └─ LoadContent()            Terraria/Main.cs:10907
```

`Main.Initialize()` 是初始化的分水岭，注意 `Terraria/Main.cs:6641-6647` 的分支：
**专用服务端（`dedServ`）走 `Initialize_AlmostEverything()` 后直接 return**，
不会初始化任何图形相关的东西。这就是 `Terraria.exe` 能用 `-server` 参数当服务端跑的原因——
客户端与服务端是**同一份代码**，只是运行期开关不同。

### 每帧的主干

```
Main.Update(GameTime)                 Terraria/Main.cs:16943
 └─ DoUpdate(ref GameTime)            Terraria/Main.cs:16997
     └─ DoUpdateInWorld()             Terraria/Main.cs:17900   （只做记录回放与计时）
         └─ DoUpdateInWorld_Inner()      Terraria/Main.cs:17918
             ├─ UpdateWorld_Players()        17998   Player.Update ×N
             ├─ UpdateWorld_SpawnNPCs()      18052   生成/刷新 NPC
             ├─ UpdateWorld_NPCs()           18072   NPC.Update ×N → NPC.AI()
             ├─ UpdateWorld_Gores()          18145   Gore 在 Projectile 之前
             ├─ UpdateWorld_Projectiles()    18170   Projectile.Update ×N → Projectile.AI()
             ├─ UpdateWorld_Items()          18198   Item.Update ×N
             ├─ UpdateWorld_Dust()           18220
             ├─ UpdateWorld_FloatingText()   18246
             └─ UpdateWorld_Time()           18257   时间/天气/事件排在主实体之后

Main.Draw(GameTime)                   Terraria/Main.cs:62562
 └─ 场景绘制 → 光照 → UI
```

> 上面这条链的细节见 [01-启动与主循环](01-启动与主循环.md)。
> **动手入口**：想知道某一帧发生了什么，就先读 `DoUpdateInWorld`，它是最短的全局提纲。

### 实体模型：数组 + 类型分支

Terraria 的"实体"不是对象树，而是**预分配的定长数组**：

| 实体 | 容器 | 规模 | 存活标记 |
| :--- | :--- | :--- | :--- |
| NPC | `Main.npc[]` | 上限 200（`InitData.MaxNPCs`，数组开到 +1） | `active` |
| 投射物 | `Main.projectile[]` | 上限 1000 | `active` |
| 玩家 | `Main.player[]` | 上限 255 | `active` |
| 掉落物 | `Main.item[]`（元素类型 `WorldItem`，不是 `Item`） | 上限 400 | `active` |

每个实体行为的分派方式是 `switch (type)` / `switch (aiStyle)` 的巨型 switch。
最典型的例子是 `Terraria/NPC.cs` 的 `AI()`——**从第 19858 行到第 41543 行，单方法约 2.17 万行**，用 `aiStyle` 做第一层分派。
（`Terraria/Projectile.cs` 的 `AI()` 同样巨型，第 23405–37466 行。）
这不是"坏代码"，而是在**闭源团队迭代二十年、无热更新**的约束下，把分派成本压到最低的务实选择。

> 为什么用巨型 switch 而非虚函数表？读 [04-实体系统](04-实体系统.md) 的"设计要点与取舍"一节。

### 数据与逻辑分离

游戏把"内容"和"行为"拆得很开：

- `Terraria.ID/*.cs`：物品、NPC、瓦片、音效的**ID 常量表**（`ItemID`、`NPCID`、`TileID`、`SoundID`）。
- `Terraria.ID/Sets`（在 `Terraria.ID/` 下）：按 ID 索引的**布尔/属性集合**，例如"这个 NPC 是不是城镇 NPC"。
- `Terraria.Localization.Content.*.json`：各语言的文本，作为**内嵌资源**打进 exe（已导出到 `resources/`）。

## 读反编译代码的心法

反编译不是原始工程，有几类"噪音"必须先学会无视或还原：

### 1. 机械变量名

```csharp
int num3 = 0;
bool flag2 = false;
Vector2 val = default(Vector2);
```
这些不是作者写的。读到它们时，**顺着它的使用方式给它起个名字再继续读**。
本仓库的文档会帮你把关键处的含义翻译好。

### 2. 语法糖被展开

| 原代码 | 反编译后 |
| :--- | :--- |
| `foreach (var x in list)` | `using (IEnumerator e = list.GetEnumerator()) { while (e.MoveNext()) ... }` |
| `using (var f = ...)` | `try { ... } finally { f.Dispose(); }` |
| `x => x + 1` | `<>c__DisplayClass` 内部类 + 实例方法 |
| `async`/`await` | `MoveNext()` + 状态机 `switch` |
| `switch`（字符串） | 哈希跳转表 |
| 对象初始化器 | 逐字段赋值 |

阅读时**在脑内折叠回去**即可，不要被结构迷惑。

### 3. 桩类型造成的注释

参见 [README](../README.md) 的"已知限制"。全树残留 465 处
`//IL_xxxxx: Unknown result type` 注释，**主要出现在 Steamworks / WeGame 平台代码（约 24 个文件）
以及少量 D3D/反射/序列化桩类型处（如 `Terraria/Main.cs`、`Terraria.Map/MapHelper.cs`、`Terraria.Graphics/TileBatch.cs`）**，
不影响游戏本体逻辑的阅读。看到它们可以直接跳过。

### 4. 静态字段的"隐式调用"

Terraria 大量使用 `Main.something` 这种全局访问，同一个字段可能被十几个子系统改写。
看到可疑状态时，用 `grep -rn "Main.<字段名>" ` 全局搜一遍赋值点，通常比顺着调用栈找更快。
