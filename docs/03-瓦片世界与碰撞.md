# 03 · 瓦片世界模型与碰撞

> 阅读约定：行号均相对 `decompiled/Terraria/`。
> 反编译丢失的是**局部变量名**而非结构，文中把 `num/flag/val` 翻译成工程含义；
> 遇到明显是编译器展开的写法（迭代器、`using`、属性 getter 的样板代码），请在脑内折叠回去再读。

## 一句话结论

《泰拉瑞亚》的世界是一张**扁平二维数组**上的 16×16 像素方格：每个格子是一个 `Tile` 对象，
用 3 个位域头（`sTileHeader`/`bTileHeader`/`bTileHeader2`/`bTileHeader3`）把十几种布尔标志塞进 8 字节；
碰撞不做真实的像素几何，而是把移动后的 AABB 与"它可能擦到的几格瓦片"做**轴分离 + 分类回退**（先判脚下、
再判左右、最后判头顶）；液体则是**另一个子系统**：维护一份"待处理格点列表"，按轮次切片逐帧扫描，
把水按水平均值回摊、向下倾倒。全世界共 2 万多个格子对象，性能靠"邻域范围小 + 按索引切片 + 跳过标记"三者共同保证。

## 关键数据结构

### Tile：一个 16×16 像素的格子

`Tile.cs:8-24` 定义了全部字段，并在 `Tile.cs:7` 标注 `[StructLayout(LayoutKind.Sequential, Pack = 1)]`：

| 字段 | 类型 | 含义 |
| :--- | :--- | :--- |
| `type` | ushort | 瓦片类型（`TileID`），0 表示无 |
| `wall` | ushort | 背景墙类型，0 表示无 |
| `liquid` | byte | 液体量，0~255（255 = 满格） |
| `sTileHeader` | ushort | 主标志位：activated/inactive/线缆/半砖/促动器/斜坡/满亮墙… |
| `bTileHeader` | byte | 液体种类（bit5-6）+ 墙漆色（bit0-4） |
| `bTileHeader2` | byte | 墙帧 X（bit0-3）、帧序号（bit4-5）、墙帧序号（bit6-7） |
| `bTileHeader3` | byte | 墙帧 Y（bit0-2）、checkingLiquid、skipLiquid、不可见、满亮块 |
| `frameX`/`frameY` | short | 图集内的像素偏移 |

重点：`Tile` 是 **class** 而非 struct（`Tile.cs:8`）。所以 `Main.tile` 数组里存的是引用，
调用方拿到 `Tile` 后直接改字段就等于改世界——不再需要"写回"。这也是全代码到处随便 `Main.tile[i, j].liquid = x` 的原因。

`sTileHeader` 的位分配可以从 getter 反推（`Tile.cs:581-735`）：

| 位 | 掩码 | 含义 |
| :--- | :--- | :--- |
| 0-4 | `0x1F` | 块漆色 `color()` |
| 5 | `0x20` | `active()`：该格是否被瓦片占用 |
| 6 | `0x40` | `inActive()`：促动器激活中，碰撞与绘制都视为不存在 |
| 7-9 | `0x80/0x100/0x200` | 四色线缆的三种（第 4 色在 `bTileHeader` bit7） |
| 10 | `0x400` | `halfBrick()`：下半砖 |
| 11 | `0x800` | `actuator()`：线缆促动器存在 |
| 12-14 | `0x7000` | `slope()`：0 无 / 1-4 四种斜坡 / 5-7 空置 |
| 15 | `0x8000` | 墙满亮 |

相邻两个属性的"语义组合"被封装成派生量：

- `nactive()`（`Tile.cs:243-250`）= `active() && !inActive()` 的**合并判断**。碰撞与物理里几乎都用它，
  因为它把"被促动器关掉的方块"当成空气处理。
- `collisionType`（`Tile.cs:73-91`）= 0 空 / 2 半砖 / 3~6 斜坡 / 1 实心块 / -1 仅顶面平台。
  注意 2 被半砖和"斜坡 0"共用，读属性时要记得区分。
- `blockType()`（`Tile.cs:204-215`）= 1 半砖 / 0 无斜坡 / 2~5 斜坡。比 `collisionType` 更"纯"，
  `IsWorldPointSolid` 就靠它做几何判定。
- `liquidType()`（`Tile.cs:233-237`）= `(bTileHeader & 0x60) >> 5`，0 水 / 1 岩浆 / 2 蜂蜜 / 3 微光（`Tile.cs:59-65`）。
  `lava()`、`honey()`、`shimmer()` 都只是"读同两位并比较"（`Tile.cs:342-394`），所以液体种类是**互斥的三态位**，
  不会出现"既岩浆又蜂蜜"。

`isTheSameAs()`（`Tile.cs:160-201`）是网络同步/AI 的"无变化检测"：先比头字，
若 `Main.tileFrameImportant[type]` 再比 `frameX/frameY`（即多格物件的帧必须一致才算相同）。
这条逻辑在客户端/服务端双向同步时省掉大量包。

### 世界的存储：一张定长二维数组

- 世界尺寸上限：`rightWorld = 134400`、`bottomWorld = 38400`（`Terraria/Main.cs:1082-1086`），
  换算成小块 `maxTilesX = rightWorld/16 + 1`、`maxTilesY = bottomWorld/16 + 1`（`Terraria/Main.cs:1088-1090`），
  即约 **8401 × 2401**。
- 实际存储只有一处：`public static Tile[,] tile = new Tile[maxTilesX, maxTilesY];`（`Terraria/Main.cs:1690`）。
- 每次新建世界会调整 `maxTilesX/maxTilesY`（`Terraria/Main.cs:5012-5023`：4200×1200 / 6400×1800 / 8400×2400 三档），
  数组本身在 `Main.Initialize` 阶段按上限一次性分配，之后不再重新分配——**世界尺寸只是逻辑裁剪**。

**关于"分块"需要澄清**：源码里确实定义了 `sectionWidth = 200`、`sectionHeight = 150`（`Terraria/Main.cs:1092-1094`），
但在客户端源码里**没有任何一处使用它们**（全仓 grep 只命中定义本身）。
真正按"区块"工作的东西在联机侧：`Main.maxSectionsX`/`maxSectionsY` 与 `Netplay.Clients[j].TileSections`
（`Terraria/Liquid.cs:1052-1060` 中重置这些标记）。结论：**瓦片数据不分块、不按需加载**；
"分块"是**网络同步的发送粒度**，以及服务端 `Netplay` 里另有一套按区块的世界文件存储（本文件未验证其实现，见延伸阅读）。
运行时"按需"的其实是**访问范围**——碰撞/液体都只碰实体附近的十几格。

### 全局类型属性表

`Tile` 上只有类型编号，绝大多数行为是**按类型查表**，这些表都是 `new bool[TileID.Count]` 级别的数组（`Terraria/Main.cs:1440-1518`）：

| 表 | 作用 |
| :--- | :--- |
| `tileSolid` / `tileSolidTop` | 是否实心 / 是否只有顶面可站（平台） |
| `tileFrameImportant` | 该类型的 frameX/Y 是否语义重要（多格物件为 true） |
| `tileCut` | 是否能被武器/挖掘直接砍掉（草、蘑菇） |
| `tileWaterDeath` / `tileLavaDeath` | 遇到水/岩浆是否会毁掉（放置时也据此禁放） |
| `tileMerge` | 与哪些类型连接时纹理合并（`Framing` 用） |

这些表是**全局可变**的：世界生成时 `WorldGen.SetBoulderSolidity(solid)` 直接改 `Main.tileSolid[138/484/664/711/712/713/714/715/716]`
（`WorldGen.cs:10959-10969`）；液体模拟里 `tilesIgnoreWater(ignoreSolids)` 会先调用 `WorldGen.SetBoulderSolidity(!ignoreSolids)`，
再切 `tileSolid[546]`（`Terraria/Liquid.cs:69-73`），即一次切换同时影响 546 与上述 9 个巨石类。
这就是为什么读代码时会看到"同一类型在不同阶段表现不同"——不是 bug，是运行期开关。

## 执行流程

### 1. 取格子：一切入口都是 `Main.tile[x, y]`

因为数组元素可能为 null（世界生成时只填部分格），所以有统一的安全访问函数
`Framing.GetTileSafely(int i, int j)`（`Framing.cs:426-439`）：越界返回一个**临时新 Tile**（不写回；越界判定用 `WorldGen.InWorld(i, j)`，
该函数 `fluff` 参数默认为 0，见 `WorldGen.cs:9633-9640`），
null 则**就地分配**再返回。注意越界分支返回的临时对象改了也白改——这是很多"看起来改了却没保存"的坑。

### 2. 世界生成期的落水：`SettleWaterAt`

世界生成时不跑逐帧液体模拟，而是调用"一次性结算"：
`Liquid.QuickWater`（`Terraria/Liquid.cs:104-148`）从最底部一行往上扫，对每格非空液体调用
`SettleWaterAt(x, y)`（`Terraria/Liquid.cs:150-289`）。

`SettleWaterAt` 的做法（按 `Terraria/Liquid.cs:150-289` 的顺序）：

1. 取出当前格液体量 `num3`，**立刻清零**（相当于把这一整滩水"端在手里"）；
2. **向下落**：一直往下走，直到下面不空（`Terraria/Liquid.cs:174-179`）；
3. **横向铺开**：在 `num4 = ±1` 的左右试探中来回摆荡，把自己倒进空的下方格
   或同一行的空格里，遇墙则掉头（`Terraria/Liquid.cs:196-270`）；
4. 把剩余液面写回最终格点（`Terraria/Liquid.cs:277-278`），再按需调用
   `AttemptToMoveLava/Honey/Shimmer`（`Terraria/Liquid.cs:280-287`）处理混液；
5. 结束时恢复 `tilesIgnoreWater(ignoreSolids: false)`。

世界生成的"多轮稳定"由 `WorldGen.cs:16173-16221` 的循环实现：先 `QuickWater(3)`（16173），
再循环调用 `Liquid.UpdateLiquid()`（16217）直到 `Liquid.numLiquid` 归零或达到轮次上限（`num < num2`）。
收尾的 `Liquid.quickSettle = false`、`worldGenTilesIgnoreWater(false)`、`Main.tileSolid[484] = false`
都在循环体之外（`WorldGen.cs:16222-16225`）。

### 3. 运行期液体：待处理列表 + 逐帧切片

运行期的液体**不是全图扫描**，而是维护一个"脏格点队列"。核心状态在 `Terraria/Liquid.cs:17-52`：

| 字段 | 含义 |
| :--- | :--- |
| `maxLiquid = 25000` / `maxLiquidBuffer = 50000` | 活跃格点上限 / 溢出缓冲上限 |
| `numLiquid` | 当前活跃格点数 |
| `curMaxLiquid` | 本帧允许的活跃上限（按画质/人数动态降） |
| `cycles` | 把一帧拆成几"趟"，每趟处理一部分 |
| `wetCounter` | 当前趟号，0~cycles-1 |
| `quickFall` / `quickSettle` | 快速下落 / 强制沉降（世界生成用） |
| `panicMode` | 积压过多时的紧急模式 |
| `stuckCount` / `stuckAmount` | 检测"液体卡住不动"的计数 |

逐步走 `Liquid.UpdateLiquid()`（`Terraria/Liquid.cs:992-1167`）：

1. `tilesIgnoreWater(true)` 临时把石块类调成非实心（`Terraria/Liquid.cs:994`），避免液体卡在正在生成的石块里；
2. 联机时按在线人数动态调 `cycles`/`curMaxLiquid`（`Terraria/Liquid.cs:995-1013`）；
3. **panic 检测**（`Terraria/Liquid.cs:1016-1029`）：缓冲量 ≥ 90% 持续 3600 帧就 `StartPanic()`；
   panic 模式下从下往上逐行 `QuickWater(0, panicY, panicY)` 硬结算，但**每帧最多回退 5 行**
   （`while (panicY >= 3 && num3 < 5)`，`panicY--` 逐帧递减，到 3 即结束并 `panicMode = false`，`Terraria/Liquid.cs:1031-1066`）；
4. **切片**（`Terraria/Liquid.cs:1078-1107`）：本趟处理 `[num4*(wetCounter-1), num4*wetCounter)` 这段索引的激活格点，
   每趟 `curMaxLiquid/cycles` 个，`wetCounter` 走满一圈（`>= cycles`）时处理尾段并归零。
   所以一帧只有 1/cycles 的脏格点真正被更新——**这是液体"看起来慢半拍"的根源，也是性能的保证**；
5. 循环内 `Main.liquid[n].Update()`（`Terraria/Liquid.cs:1100-1107`）：若格点被标 `skipLiquid` 就跳过；
6. **回收**（`Terraria/Liquid.cs:1115-1159`）：把 `kill >= 10`（`num`，即连续 10 趟没变化）的格点从活跃表移除；
   把缓冲区里的格点补进活跃表（`AddWater` + `LiquidBuffer.DelBuffer`）；
   若活跃格点数量长期几乎不变（`stuckAmount ± 50` 持续 10000 次），判定"液体卡死"全部清空；
7. 联机广播改动的格点（`Terraria/Liquid.cs:1160-1165`，`NetLiquidModule`），最后恢复实心设置。

> 一个源码层面的疑点：`wetCounter++` 只出现在 `Terraria/Liquid.cs:1078`，`AddWater`/`Liquid.Update` 内部都不再推进它，
> 所以 `UpdateLiquid` 每被调用一次最多只推进一趟切片。全仓共 4 处调用：`WorldGen.cs:16217`、`WorldGen.cs:21390`、
> `WorldGen.cs:71893`、`WorldFile.cs:765`，均不在逐帧的主更新循环中。其中 `Terraria/WorldGen.cs:71891-71893` 位于
> `using (Main.SwapRandom("UpdateLiquid"))` 作用域内，并受 `Liquid.skipCount > 1` 节流，疑似主循环的液体更新入口；
> 该调用链未能完全验证，这里只陈述代码事实，不做推断。

### 4. 单个格点的液体步进：`Liquid.Update()`（`Terraria/Liquid.cs:451-963`）

入队时 `AddWater(x, y)` 会把格点写进 `Main.liquid[numLiquid]`（`Terraria/Liquid.cs:1181-1187`），
并设置 `checkingLiquid = true` 防止重复入队（`Terraria/Liquid.cs:1181`，标志位见 `Tile.cs:496-512`）。

`Update()` 的步骤：

1. **实心格自杀**：若本体是实心块，`kill = 999` 立即退场（`Terraria/Liquid.cs:460-466`）；
2. **地狱蒸发**（`Terraria/Liquid.cs:468-477`）：`y > Main.UnderworldLayer` 的水每趟减少最多 2（岩浆不受影响）；
3. **混液**：岩浆走 `LavaCheck`，水/蜂蜜/微光走对应分支，互相 `AddWater` 唤醒邻格（`Terraria/Liquid.cs:481-568`）；
4. **向下优先**（`Terraria/Liquid.cs:569-611`）：下方可通行、下方液体量未满、种类相同 → 转移 `min(255-下方量, 本格量)`；
5. **横向摊平**（`Terraria/Liquid.cs:612-948`）：以本格为中心，分别探测 ±1、±2、±3 格的左右是否"可流"
   （可流 = 非实心、空或有同种液体），然后从 7 格 / 5 格 / 4 格 / 3 格 / 2 格的窗口里取**平均值**回填。
   这就是"水面自动找平"的全部实现：不是物理，而是**局部均值滤波**；
6. **变化追踪**（`Terraria/Liquid.cs:949-972`）：本趟液体量变了 → `kill = 0` 并把上方格重新入队（可能塌陷）；
   没变 → `kill++`，用于第 3 步的回收判定。例外是满格回升特判：本趟由 254 回升到 255 时不入队，
   而是走 `kill++`（`quickSettle` 时先把本格设为 255 再 `kill++`，`Terraria/Liquid.cs:951-962`）。

`num2 = -1` 的小细节（`Terraria/Liquid.cs:680-686`）：本格液体 < 3 时，均值计算里补一个 -1，
模拟"蒸发/表面张力"，防止薄水层无限摊平。

**混液产物的类型编号**由 `GetLiquidMergeTypes`（`Terraria/Liquid.cs:1386-1454`）查表得到：
水+岩浆→黑曜石(56)，岩浆+蜂蜜→松香块(230)，蜂蜜+水→蜂蜜块(229)，微光与任何液体→微光块(659)。
凝固的条件不是单纯的液量阈值（`Terraria/Liquid.cs:1269-1270`）：周边异种液体积 `num >= 24`、
`liquidMergeType != 本格类型`、且目标格未被占用或可被黑曜石类摧毁（`!tile5.active() || Main.tileObsidianKill[tile5.type]`）
三者同时满足；本格液量 `< 24` 时走另一分支——直接把本格液体清零并广播（`Terraria/Liquid.cs:1299-1308`）。

### 5. 碰撞：先把"意图位置"与邻格做 AABB

`Collision.TileCollision`（`Terraria/Collision.cs:2299-2460`）是几乎所有实体（玩家、NPC、投射物）共用的瓦片碰撞：

1. **扫描范围**（`Terraria/Collision.cs:2306-2316`）：
   `[Position.X/16 - 1, (Position.X+Width)/16 + 2]` × `[Position.Y/16 - 1, (Position.Y+Height)/16 + 2]`，
   比实际包围盒各多扩 1~2 格，避免高速移动漏检；随后夹到 `[0, maxTilesY - 40]`——注意**底部 40 格被排除**，
   地狱底层不参与碰撞。
2. **实心判定**（`Terraria/Collision.cs:2323-2344`）：
   `Main.tileSolid[type]` 为真，或 `tileSolidTop[type] && frameY == 0`（平台的"顶面"那帧）；
   `inActive()` 的方块直接跳过；可选参数 `ignoreDoors` 让关门不挡碰撞（`TileID.Sets.ForAdvancedCollision.ClosedDoors`），
   `ignoreAetheriumPlatforms` 特判平台 `type == 19 && frameY/18 == 50`。
3. **半砖收缩**（`Terraria/Collision.cs:2346-2352`）：半砖时碰撞高度由 16 变 8，顶部下移 8。
4. **AABB 粗筛**（`Terraria/Collision.cs:2353-2356`）：用"移动后的 AABB" 与"格子矩形"做四次比较，
   不相交直接跳过——这是整条流程最热的那几行。
5. **斜坡"放行"**（`Terraria/Collision.cs:2357-2381`）：若斜坡朝向与移动方向一致
   （下坡 slope 3/4、上坡 slope 1/2），且实体紧贴斜率边缘，则标 `flag3` 跳过该格。
   这就是"人物沿斜坡滑下不卡顿"的实现——本质是**允许穿模的例外规则**。
6. **轴分离回退**（`Terraria/Collision.cs:2382-2441`），按优先级依次判断：
   - 原位置底边在上方格顶之下 → **下落**，把 `result.Y` 夹到瓦片顶（并设 `down = true`）；
   - 否则左侧、右侧 → 把 `result.X` 夹到瓦片边（`hoik` 参数允许"钩穿"贴墙的斜坡）；
   - 否则头顶 → 把 `result.Y` 夹到瓦片底（`up = true`）；分离量按重力方向加：正常重力 `gravDir == 1` 时加 `0.01`，
     反向重力不加（`Terraria/Collision.cs:2451`）。反向的"下落"分支同理，只有 `gravDir == -1` 时加 `-0.01`（`Terraria/Collision.cs:2401`）。
   四个静态输出字段 `up/down/sloping/stair`（`Terraria/Collision.cs:45-61`）就是这一步的副产物，调用方靠它们判断"是否落地/撞头"。

`noSlopeCollision`（`Terraria/Collision.cs:2038-2137`）是同一算法的**简化版**：去掉斜坡放行与斜坡回退，
用于方块单块物理；`BuildTileContacts`（`Terraria/Collision.cs:2140-2297`）则改用"接触面"模型，
输出了 `TileContact` 列表（左/右/顶/底/左下/右下，`Terraria/Collision.cs:11-38`），供新式物理/矿车等使用。

`SolidTiles`（`Terraria/Collision.cs:3468-3501`）是布尔版：只问"这一矩形里有没有实心块"，越界直接返回 true（把世界外当实心）。

### 6. 台阶与斜坡的"人味"

玩家/NPC 不会自动走上 1 格高的台阶，靠的是 `StepUp`（`Terraria/Collision.cs:3641-3789`）：

1. 取"下一帧的水平中线"所在的列，找脚下那一格（`Terraria/Collision.cs:3653-3661`）；
2. 检查台阶上方 `height/16+2` 格是否都空（`flag`）、旁边那格是否空（`flag2`），
   不满足就放弃抬升（`Terraria/Collision.cs:3675-3691`）；
3. 再要求"台阶顶端那一格"是实心或顶面可站（`flag3/flag4`）；`holdsMatching` 为真时允许踩上平台
   （`tileSolidTop && frameY == 0`）（`Terraria/Collision.cs:3699-3719`）；
4. 抬升幅度 ≤ 16.1 像素：`position.Y` 吸附到台阶顶，并把抬升量累加进 `gfxOffY`（**只影响绘制，不影响物理位置**），
   让玩家看起来是"平滑走上去"而不是瞬移；抬升 < 9 像素设 `stepSpeed = 1`，否则 2（`Terraria/Collision.cs:3741-3769`）。

反向的 `StepDown`（`Terraria/Collision.cs:3577-3639`）做镜像处理：脚下悬空则往下吸附。

`IsWorldPointSolid`（`Terraria/Collision.cs:1437-1494`）是"点是否在实心体内"的精确版：
先 `toTileCoordinates`，再按 `blockType()` 分支——半砖要求点在低半格，斜坡用 `(pos.X % 16, pos.Y % 16)` 的线性不等式
（`slope 3: x+y >= 16`、`slope 2: y >= x` 等）判 **三角形内**。这是少数真正按几何判定的函数。

### 7. 液体与实体的交互

液体的"可站表面"和"淹没判定"是两套不同的逻辑：

- `DrownCollision`（`Terraria/Collision.cs:1385-1435`）：**头部**区域（约 10×12 的小盒）是否泡在非岩浆非微光液体里。
  关键公式：`num6 = (256 - liquid) / 32` 得到"距离满格还差多少像素 ×2"，用它把格子顶部的液面高度换算成像素
  （`Terraria/Collision.cs:1424-1427`）。液体量 255 → 液面到格顶；液体 0 → 无。
- `WaterCollision`（`Terraria/Collision.cs:2793-2824`）：只处理"本格有液体、上方格无液体"的**表面格**，
  液面高度 `num2 = liquid/32*2 + 2`（`Terraria/Collision.cs:2810`），实体从上方落时把 `result.Y` 夹到液面——
  这就是"水上行走/液体顶面可站"的实现依据。
- `LiquidPlace` / `CheckWaterDeath` / `CheckLavaDeath`（`Terraria.ObjectData/TileObjectData.cs:5045-5120`）：
  放置时液体是否允许（岩浆遇 `tileLavaDeath` 类型禁放），运行期液面上升是否会毁掉物件。
  优先级是"物件自有规则 > 全局 `Main.tileWaterDeath` 表"（`Terraria.ObjectData/TileObjectData.cs:5074-5096`）。

### 8. 多格物件：`TileObjectData`

家具、门、雕像这些占多格的物件，**不是**一个数据结构体，而是**同一组 Tile 各自存一个图集帧**，
布局信息在全局表 `TileObjectData._data`（`Terraria.ObjectData/TileObjectData.cs:69`）里按类型索引。核心属性：

| 属性 | 含义 |
| :--- | :--- |
| `Width` / `Height` | 占几格宽/高（`Terraria.ObjectData/TileObjectData.cs:1174/1213`） |
| `Origin` | 哪个格是"原点"（放下时鼠标所指那格），如 3×4 门的原点常在底下两格之外（`Terraria.ObjectData/TileObjectData.cs:1252`） |
| `CoordinateWidth` / `CoordinateHeights` | 每一格在图集里的像素尺寸（通常 16，也有 18/20/38 的特殊值，`Terraria.ObjectData/TileObjectData.cs:2168-2357`） |
| `CoordinateFullWidth/Height` | 一个"样式"在图集里占的总像素（由 `Calculate()` 累加得出，`Terraria.ObjectData/TileObjectData.cs:1805-1833`） |
| `StyleHorizontal` / `StyleWrapLimit` / `StyleMultiplier` | 图集里同一类型的多个样式如何换行 |
| `AnchorValidTiles` / `AnchorTop/Bottom/Left/Right` | 允许贴靠的方块类型与"必须贴着"的边 |
| `LavaDeath` / `WaterDeath` / `WaterPlacement` / `LavaPlacement` | 液体相关规则 |

**放置流程**（`TileObject.Place`，`TileObject.cs:176-...`）：
`x - Origin.X`、`y - Origin.Y` 得到左上角（`TileObject.cs:182-183`），再按 `AnchorTop/Bottom` 扩展需要检查的矩形，
逐格验证锚点与空间，最后把 `width×height` 个格写入 `type`、`frameX/frameY`。
朝向由 `Direction == PlaceLeft/PlaceRight` 决定，会在候选 `Alternates` 中排除反向样式（`TileObject.cs:207-211`）。

**反向查询**（`GetTileData(Tile)`，`Terraria.ObjectData/TileObjectData.cs:5197-5262`）是最容易读错的一段，它从 `frameX/frameY` 反推样式：
1. `x/16` 得列、`y/16` 得行；
2. 若 `StyleWrapLimit > 0`，用 `行*limit + 列`（或横向时 `列*limit + 行`）得到"第几个样式"；
3. `StyleMultiplier` 把"第几个样式"拆成(`样式`, `余数`)：`num5 = 商`、`num6 = 余数`；
4. 用商去 `SubTiles` 里挑子样式；再用余数在 `Alternates` 里按 `Style <= num6 <= Style+RandomStyleRange` 匹配备用样式。

**"帧是否重要"开关**：`Main.tileFrameImportant[type]` 为 true 的类型，其 `frameX/frameY` 参与相等性判断
（`Tile.cs:171-174`）——这类物件在放置/摧毁时必须**整体同步**，否则会出现"半张桌子"。

### 9. 邻接与纹理合并：`Framing`

`Framing.SelfFrame8Way`（`Framing.cs:193-...`）只在**纹理层面**工作：它用 `GetTileSafely` 取 8 个邻居
（`Framing.cs:204/221/238/255/271...`），按 `WillItBlend` 决定是否与邻居融合（`Framing.cs:205-216`），
最后用位掩码 `num |= 1/2/4/8` 表示上/左/右/下邻居（`Framing.cs:210/227/244/261`），写回 `frameX/frameY`。
它**不改物理属性**——只改图集偏移，所以读碰撞代码时不需要关心 Framing。

## 设计要点与取舍

1. **Tile 是"宽对象"，不是 SOA**。一个格子 8 个字段，全世界 ~2000 万格 = 上千万个 class 实例，
   内存开销巨大，但换来"任意格子可独立赋任何属性组合"的表达力，且 `Main.tile[i,j]` 一维索引访问极快。
   代价是缓存局部性差——这也是 Terraria 在 1080p 下能跑的极限来源之一。
2. **行为外置成类型表**。`tileSolid` 等数组可运行期改写（`WorldGen.cs:10959`），
   所以"实心性"是**阶段相关的动态属性**。写代码时不能假设`tileSolid[X]`恒定。
3. **碰撞是"保守扫描 + 例外放行"**。范围多扩 1~2 格、先粗筛再按轴判，宁可多扫几格不漏检；
   斜坡用"方向相同就放行"的启发式，不做真实线-多边形求交。好处是代码短、稳定，坏处是高速移动仍可能穿透
   （所以有 `TileCollisionInStepsOf16`，`Terraria/Collision.cs:2462-2493`，以 16 像素为步长分步检测，
   返回沿给定方向可前进的距离；紧随其后的 `TryChangingSizeFromBottomCenter`（`Terraria/Collision.cs:2495` 起）也复用它）。
4. **底部 40 格不参与碰撞**（`Terraria/Collision.cs:2314-2315`、`Terraria/Collision.cs:3468-3482`）。地狱底层是"世界边框"，宁可角色掉下去也不做特殊处理。
5. **液体是"局部平均滤波"而非流体力学**。平均窗口 7/5/4/3/2 格由"两侧是否可流"决定（`Terraria/Liquid.cs:612-948`），
   向下永远优先于横向；如此才在一帧内用几万次算术完成"看起来像水"的效果。
6. **液体按索引切片**（`cycles` 趟/帧）。一帧只更新 1/cycles 的脏格点，用"延迟"换"峰值 CPU"；
   调试时看到的"水面抖动"很多是切片造成的相位差，而非算法错误。
7. **多格物件不是"复合实体"**。它没有独立的包围盒，每个格子独立存在、独立参与碰撞（门/平台的碰撞靠
   `tileSolidTop` + `frameY` 区分），布局信息只存在于全局 `TileObjectData` 表里。这解释了为什么摧毁家具时
   常常需要调用方自己循环清掉周围的格子。
